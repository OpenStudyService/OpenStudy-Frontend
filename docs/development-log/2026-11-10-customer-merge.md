# 중복 고객 확인과 병합

## 배경

Frontend #41은 사장님이 동일 연락처의 중복 후보를 찾고 두 고객의 이력을 검토한 뒤 병합하는 화면을 요구한다. Backend #204가 이미 병합돼 Backend main 16a4748의 OpenAPI와 ADR-M13-001을 기준으로 구현했다.

## 결정 및 이유

- 화면 진입점은 동일 연락처 후보 목록에 두었다. 두 고객을 직접 선택하고 기존 결제·이용권 이력을 읽어야 제출할 수 있다. 대상과 흡수 고객의 버전을 함께 보내고, 충돌하면 입력을 보존한 채 최신 정보를 확인한 뒤 재제출하도록 했다.
- 이전 거래의 참조를 보존한다는 정책을 따라 병합된 고객의 상태와 대상 링크를 표시했다. 고객을 열람할 수 있는 직원은 읽기 전용 병합 이력도 볼 수 있다. 대상 상세에서는 흡수 고객의 원래 참조가 포함된 공간 이력을 수용하되 지점 범위와 중복 ID 검사는 계속 적용한다.
- #40과 독립적으로 main에 제안할 수 있도록 병합 계약의 변경만 생성 타입에 반영했다. 충돌 응답은 공통 오류에 병합 대상 ID를 더해 표현한다.

## 구현

- OWNER에게만 후보 조회·이력 비교·사유 입력·병합을 제공한다. 병합이 되돌릴 수 없음을 안내한다.
- 기본 고객 목록에서 병합된 고객을 제외하고 상태 필터로 따로 조회한다. 흡수 고객 상세는 상태·대상 링크를, 대상 상세는 흡수 고객 수를 표시한다.
- 고객 수정·상태 변경, 판매·예약·사물함 배정·입실의 병합 충돌에서 대상 고객으로 안내한다.
- MSW에서 후보 집계, 이력과 기존 고객 참조 보존, 연쇄 병합, 대상의 흡수 이용권 입실을 구현했다.

## 검증 결과

| 인수 조건 | 구현 및 검증 |
| --- | --- |
| live 후보 조회·비교·병합 | 로컬 Backend main과 Chrome에서 후보 조회부터 병합까지 통과. 버전 충돌에서 대상 선택·흡수 고객 선택·사유가 유지되고 최신 데이터를 읽어 다시 병합할 수 있음을 확인. |
| 사전 안내와 두 이력 | 실제 Chrome에서 되돌릴 수 없다는 문구와 두 고객의 결제·이용권 이력이 보이는 것을 확인. 데모 Chrome에서도 빈 이력을 포함해 두 고객 비교 확인. |
| 흡수 고객 상태와 링크 | 실제 일반 직원 세션에서 병합됨·병합 이력을 열고 대상 고객으로 이동. 데모 Chrome에서 상태 필터를 사용한 조회와 링크 이동 확인. |
| OWNER 제한 | 실제 일반 직원 세션에서 후보 버튼 숨김, 후보 조회·병합 API 403 확인. MSW 권한 계약 통과. |

- 실제 API에서 자기 병합 422, 병합 재요청 409, 판매·예약·사물함 배정·입실의 CUSTOMER_NOT_ACTIVE와 mergedIntoCustomerId를 확인했다. 실제 Chrome에서 흡수 고객 회원번호로 대상 고객을 찾아 흡수 고객 이용권으로 입실했다.
- MSW에서 고객 수정·상태 변경의 CUSTOMER_ALREADY_MERGED, 연쇄 병합 이력과 기존 이용권 참조 보존까지 검증했다.
- typecheck, lint, 전체 Vitest 654개, 관련 Vitest 637개, live·demo 빌드와 번들 격리 검사, graphify AST 갱신이 통과했다. SQL 파서가 설치되지 않아 SQL 파일 3개는 그래프에 포함되지 않았다.
- 전체·관련 테스트의 동시 실행에서 기존 AI 계약 테스트 한 건이 5초 제한을 넘겼다. 워커를 4개로 제한한 순차 재실행에서는 두 테스트 집합이 모두 통과했다.
- Chrome live 1개, mock 1개를 각각 통과했다. 검증용 Backend·MySQL 컨테이너, 전용 네트워크와 임시 비밀번호를 정리했다.

## 후속 작업

- 운영 배포 환경 및 모바일 실기기 검증은 별도다. 거래 오류 링크는 공통 화면 요소를 사용하며 네 화면의 오류 이후 클릭을 실제 Chrome으로 개별 재현하지는 않았다.
