# 2026-11-11 AI 분석 결과 재사용

## 1. 배경 / 문제

- Frontend #46의 FR-NL-22·23·25·35에 따라 적용 조건, 조건 변경, 최근 질문, 후속 질문 문맥, 서버 표 조회를 연결해야 했다.
- Backend 원격 main `6e07292`의 M15 계약과 구현을 확인했다. ADR-M15-001의 M15-D04 개정으로 저장된 실행은 요청마다 현재 권한으로 다시 실행되고 계획 만료는 발생하지 않는다.

## 2. 검토한 선택지

- 기존 질문 경로인 `POST /ai/queries`의 전체 응답에는 문맥이 들어온다. 접수 전용 경로를 사용하면 문맥을 곧바로 표시할 수 없어 기존 경로를 유지했다.
- 기존 표는 브라우저에 들어온 행을 정렬했다. 실행 ID가 있는 결과의 표는 서버가 현재 권한과 기준 시각으로 다시 조회하고, 받은 페이지와 행 수를 사용하도록 연결했다.

## 3. 결정 및 이유

- 사용자와 합의한 배치에 따라 대화 기록 옆에 **최근 질문**, 적용 조건 아래에 **조건 변경**, 차트 옆에 **표로 보기**를 배치했다. 표 선택 항목은 **데이터 종류**, 문맥은 **유지**와 **변경된 조건**으로 표시한다.
- 최근 질문의 저장 실행은 결과만 다시 조회한다. 그 결과에서 조건을 변경하면 원래 대화에 새 실행이 저장된다. 저장 실행을 다시 조회한 뒤 새로 질문하면 새 대화에서 해석한다.
- 서버의 `editableFilters`와 세션 권한으로 편집 가능 범위를 정한다. 바뀐 조건만 전송하고, 같은 본문을 다시 제출할 때는 같은 요청 키를 사용한다.
- Backend 원격 main의 OpenAPI를 임시 사본으로 꺼내 타입을 다시 생성했다. Frontend main에는 #125의 정의가 이미 들어 있었고, 이번 생성으로 #126의 질문 응답 필드 세 개가 반영됐다.

## 4. 구현 내용

- 결과에 적용 조건과 후속 질문 문맥을 표시한다. 범위 변경과 권한 상실 사유는 별도로 표시한다. 첫 질문의 `NO_PRIOR_RESULT`는 경고로 표시하지 않는다.
- 조건 변경은 같은 대화의 새 실행으로 표시한다. 최근 질문 탭은 저장 실행의 재조회와 새 질문 제출을 구분한다. 재사용 거절 시 사유와 범위 축소 또는 다시 질문하기를 안내한다.
- `Ai.tsx` 결과 카드는 기존 ViewSpec 차트에 조건 영역과 서버 표를 연결했다. 표는 현재 차트의 데이터 종류부터 열고 데이터 종류 선택, 열 정렬, 페이지 이동, 재조회 기준 시각을 제공한다. #47과 병행할 때 `Ai.tsx`, 생성 타입, `src/mocks`를 함께 확인한다.
- AI 목업은 `src/mocks/ai.ts`로 모았다. 저장 실행, 최근 질문의 사용자·기간·건수 범위, 조건 변경과 오류, 후속 질문 문맥, 표 페이지와 정렬을 재현한다.

## 5. 검증 결과

- `npm run typecheck`, `npm run lint`, `npm test` 전체 단위 테스트 83개 파일 735개, `npm run build` 및 `check:build:live` 통과.
- 단위 테스트와 MSW 계약 테스트에서 변경 필드만 전송, 기간·지점·상품 제한, 저장 실행의 소유권과 재검증, 최근 질문의 본인 범위와 30일·20건 제한, 문맥 구분과 끊김 사유, 데이터 종류·페이지·열 정렬, 네 가지 403 사유 안내와 대화 삭제 후 404를 확인했다.
- 전체 테스트의 기존 업무 담당자 조회 경고와 Vite의 500 kB 초과 청크 경고를 확인했다. 두 명령 모두 성공했다.
- 실제 API 연결, 통합 테스트 및 Playwright E2E는 마일스톤 검증으로 미룸(미실행). 새 worktree에 `graphify-out/graph.json`이 없어 그래프 조회와 갱신은 생략했다.

## 6. 남은 작업 / 보류 사항

- Backend 원격 main의 대화 다시 열기는 수정 실행의 `origin`·`sourceExecutionId`와 재계산 결과를 반환하지만, 실행 자체의 `response.executionId`·`conditions`·`editableFilters`는 null이다. 다시 연 결과에는 기존 표·차트를 표시하며, 실행 ID와 조건이 제공되면 조건 변경과 서버 표 조회를 사용할 수 있다. 적용 조건 표시와 서버 재사용의 전체 범위를 위해 백엔드 응답 확인이 필요하다.
- `GET /ai/executions/{executionId}` 응답에는 `truncation` 구조가 없다. 화면은 질문 응답의 잘림 정보와 재조회 응답의 `warnings`를 표시한다. 재조회에서 새로 발생한 잘림은 서버가 알림을 제공하는 범위에서 표시할 수 있다.
