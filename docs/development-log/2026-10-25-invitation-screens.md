# 2026-10-25 F03 초대 관리·수락·승인 상태 화면

## 1. 배경 / 문제

Frontend #6(F03)의 기존 화면은 범용 리소스 폼, GET 쿼리 토큰 미리보기, 수락 시 자동 세션 발급을 가정했다. 확정 기반 계약은 fragment 토큰의 POST 미리보기, 신규·기존 계정 수락 구분, 별도 본인 승인 조회와 승인 후 재로그인을 요구한다. Backend B07~B09는 이번 작업 시점에 운영 API가 구현되지 않아 실제 서버·메일 검증을 분리해야 한다.

## 2. 검토한 선택지

기존 범용 리소스 화면을 계속 확장하거나 초대 전용 화면을 만드는 방법을 검토했다. 초대 상태와 메일 발송 상태, 수락 모드, 승인·반려·재발급 가능 상태가 서로 달라 범용 폼으로는 계약과 권한을 드러내기 어려웠다.

## 3. 결정 및 이유

기존 직원 관리의 `tab=invitations` 경로를 유지하면서 전용 초대 관리·수락·승인 상태 컴포넌트를 연결했다. 정본 `foundation.generated.ts` 타입을 재사용한다. 백엔드 미구현 상태에서는 MSW 계약 fixture와 UI 테스트를 진행하고 서버의 실제 인가·세션·발송 증거로 해석하지 않는다.

토큰은 fragment에서 읽어 수락 컴포넌트 수명 동안만 보관한다. 브라우저 주소에서 fragment와 기존 쿼리 token을 제거하고 POST 본문으로만 전송한다. React Query 키·캐시, 브라우저 저장소 또는 관리자 응답에 토큰·비밀번호를 저장하지 않는다. 신규 수락 응답은 인증 세션으로 취급하지 않는다.

## 4. 구현 내용

- 관리자 목록에서 초대 상태·발송 상태를 분리하고 검색·페이지·상태 필터를 제공한다. 관리자 DTO에는 메일 링크가 없다.
- STAFF 기본 예정 권한은 빈 배열, MANAGER는 9종 기본 권한을 복사한다. 지점 관리자는 STAFF만 초대하며 MANAGER 초대 처리는 사장님만 표시한다.
- version을 전달하는 재발급·취소·승인·반려와 409 입력 보존·최신 조회를 제공한다. 재발급 새24시간, 자동 재시도 TTL 유지, 수락 후 승인 대기 무기한을 안내한다.
- 신규 계정은 비밀번호 설정 후 로그인하여 승인 상태를 확인한다. 기존 계정은 같은 이메일로 로그인한 뒤 비밀번호 없이 수락하고 기존 지점 업무를 유지한다. 다른 계정으로 신규 수락한 경우 로그인 이동 전에 기존 세션을 종료한다.
- 본인 승인 상태를 15초마다 조회하고 반려 사유를 표시한다. 승인된 제한 세션은 로그아웃·재로그인을 요구한다. 기존 활성 직원은 기존 지점 업무 복귀 링크를 사용할 수 있다.
- 문서 Referrer-Policy를 `no-referrer`로 설정한다. 기존 MSW quiet 모드를 유지한다.
- MSW fixture에서 CSRF·본인 이메일·역할·version·재발급 이전 링크 폐기·회수 소속 복구·제한 계정 활성화 금지를 검증한다. 발송 링크 더블은 테스트용 메모리에만 존재하며 실제 이메일을 보내지 않는다. fixture 초대 데이터는 전체 문서 새로고침 때 초기화되므로 실제 서버의 내구성 검증을 대신하지 않는다. 제한 세션 모드만 비밀값 없이 데모 저장소에 보존한다.
- 기존 범용 링크 노출 E2E를 전용 계약 흐름 테스트로 대체했다. 같은 수락 경로에서 새 fragment로 이동할 때 이전 미리보기 상태가 남던 회귀를 Chrome 검증에서 찾아 수정했다.

## 5. 검증 결과

- TypeScript, ESLint, 전체 Vitest 90개(13개 파일), live 빌드 통과.
- Chrome Playwright 4개 흐름 통과: 신규 수락→로그인→승인 대기→승인 완료→재로그인→업무, 누락/만료 fragment와 GET 쿼리 토큰 미사용, 구조화 지점 운영시간 등록, 단일 지점 소속과 두 version 전달·이메일 보존.
- React Query 캐시에 토큰이 없는지, 수락 본문 모드와 비밀번호 유무, 관리자 DTO/저장소에 원문 비밀값이 없는지 단위·계약 테스트로 검사했다.
- 기본 브라우저 스킬의 `ego-browser` 명령이 설치되지 않아 기존 Playwright Chrome 검증을 사용했다.

## 6. 남은 작업 / 보류 사항

- B07~B09 실제 API·SMTP/메일 더블을 통한 실제 수신 링크·두 브라우저 간 승인 갱신·서버 인가 및 CSRF 검증은 미실행이다.
- 실제 서버의 프로세스 재시작·메일 retry·lease·동시 수락·승인/반려 경합은 백엔드 및 V01 검증 대상이다.
- #6은 전체 완료 또는 자동 종료 처리하지 않는다. 작업 브랜치 PR의 main 병합은 사용자가 수행한다.
