# 2026-10-29 — Frontend #19 회원 관리의 실제 고객 API 연결

## 1. 배경 / 문제

[Frontend #19](https://github.com/OpenStudyService/OpenStudy-Frontend/issues/19)는 기존 회원 데모를 고객 원장 API에 연결하는 작업이다. [Backend #55~#58](https://github.com/OpenStudyService/OpenStudy-Backend/issues/55)의 계약·고객·결제·환불 구현은 PR #132~#135로 main에 병합됐다. 기존 화면은 `/members`와 평면 데모 모델을 사용해 정본 `/customers`의 회원번호, 등록 지점, 목록 최소 필드, `canEdit`, version 및 상태 변경 사유를 표현하지 못했다.

사용자가 서브 에이전트를 활용한 #19 구현을 요청했다. 최신 Frontend main `b29aa7b`에서 `feature/customer-management`를 만들었다. UI·MSW 계약/시험·브라우저/실서버 검증을 서브 에이전트에 나누고, 주 에이전트는 정본 타입·조회 인터페이스·메뉴 연결·통합 검증 및 변경 검토를 담당했다. 같은 브랜치에서 파일 소유 범위를 나눠 작업했다.

Backend는 별도 `feature/seat-usage-api-contract` 작업 중이므로 소스·DB를 변경하지 않았다. 정본은 Backend 원격 main `8eb2af6`(환불 PR #135 병합)을 기준으로 고정했다. 작업 전부터 있던 미추적 `.gitattributes`는 제외한다.

## 2. 검토한 선택지

- 범용 목록·폼에 고객 계약 분기를 모두 넣으면 이미 다른 모듈이 사용하는 데모 필드와 고객의 읽기/쓰기 권한이 섞인다. 기존 표·검색·상세 패널 디자인과 `/app/:scope/members` URL을 유지하면서 `features/customers`로 분리하고 범용 진입점에서 위임했다. 보유 이용권 탭은 유지한다.
- 편집 중 재조회 결과로 폼을 교체하면 입력을 잃는다. 편집 원본·초안·명시적으로 조회한 최신 고객을 별도로 유지하고, 서버 `canEdit`을 변경 가능 여부의 근거로 사용한다. 등록 지점의 권한만으로 수정 가능 여부를 추정하지 않는다. 결제 지점의 권한으로 수정할 수도 있기 때문이다.
- 데모 고객을 새 저장소에 복제하면 기존 결제·좌석 흐름과 ID·상태가 어긋난다. 기존 `db.members`와 ID를 공유하고, 선택적 데모 메타데이터와 어댑터로 정본 응답을 만든다.
- 실제 입력을 포함한 데모 DB 전체를 sessionStorage에 저장하는 기존 방식은 #19의 개인정보 조건에 맞지 않는다. 고객 변경과 생성 멱등 결과는 메모리에서만 유지하고, 전체 페이지 새로고침 시 고정된 합성 회원 fixture로 복원한다. 실제 저장 지속성은 별도 MySQL·Backend에서 검증했다.

## 3. 결정 및 이유

- 목록은 회원번호·이름·연락처·상태·등록 지점·등록 시각만 표시한다. 이메일·응대 메모·상태 사유는 상세에서만 조회한다. 검색·상태·정렬·방향·페이지·페이지 크기는 URL에 유지하고 조건 변경 시 첫 페이지로 이동한다. 페이지 계산은 서버 meta를 따르며 크기는 최대 100이다.
- 등록은 명시한 운영 지점의 `members:write`를 요구한다. 전체 지점 화면에서는 실제 지점을 먼저 고른다. 회원번호·등록 지점·상태는 일반 수정 요청에 넣지 않는다. 상태 변경은 별도 API와 사유 입력을 사용한다. 삭제는 제공하지 않는다.
- 409에서는 입력을 유지하고 최신 조회 성공 전 재저장을 막는다. 최신값을 확인해도 자동 재전송하지 않으며, 사용자가 다시 저장하면 원본 대비 변경한 필드만 최신 version에 적용한다. 상태 충돌도 최신값을 확인한 뒤 명시적으로 다시 실행한다.
- 422와 네트워크 오류는 입력을 보존한다. 편집 중 배경 상세 조회의 일시적 5xx 때문에 폼을 제거하지 않고 재시도를 제공한다. 반면 401/403/404와 변경 권한 회수는 편집을 제거한다. 계정·지점·권한 문맥이 바뀌면 요청을 중단하고 이전 초안을 정리한다.
- 저장 중 동기 잠금으로 이중 제출을 막는다. 고객 생성 재시도는 같은 논리 요청의 멱등 키를 유지한다. 저장하지 않은 입력에는 패널 닫기·라우터 이동·새로고침 이탈 확인을 적용한다.
- 개인정보를 localStorage/sessionStorage나 분석 로그에 추가하지 않는다. 데모 회원 입력 외에도 이전 데모의 고객 멱등 결과와 개인정보가 포함된 회원 감사 스냅샷을 저장 대상에서 제외한다. 새 감사 기록에는 변경 필드 이름만 남긴다.
- 미확정 API·실패 대체·live 가짜 성공은 추가하지 않는다. 구매·사용 내역과 타 지점 최소 요약은 #22·#25 범위다. 결제·보유 이용권·환불 화면 연결인 #20은 구현하지 않는다.

## 4. 구현 내용

- `features/customers/`: 목록, 등록·수정 폼, 상세·상태 패널, 정본 타입 별칭, 입력 검증·변경 필드 계산, HTTP 어댑터, 조회/변경 훅 및 모델·어댑터·UI 시험.
- 기존 `ResourcePage`와 `RecordPanel`의 회원 진입만 새 화면에 위임한다. 회원·이용권 메뉴와 보유 이용권 탭은 유지하며 다른 범용 화면은 재구성하지 않았다.
- `customerApi.list(scope, filters, signal)`과 정본 `CustomerListItem`·`CustomerPage`를 #20 고객 선택에서도 재사용할 수 있다. 캐시 접두사는 `[data, userId, scope, customers]`이고 상세는 여기에 `detail, id`를 붙인다. 저장 성공 후 사용자 데이터와 관련 선택 데이터를 다시 조회한다.
- Backend 작업 중 OpenAPI가 섞이지 않도록 `git show origin/main:docs/design/foundation/openapi.json`으로 고정한 정본에 기존 `api:foundation`과 같은 `openapi-typescript`·Prettier 생성기를 적용했다. 생성 타입에는 이미 확정된 M4 고객·결제·이용권 operation이 함께 추가된다. Backend 파일은 변경하지 않는다.
- `mocks/customers.ts`: `/api/customers` 5개 operation. 등록 지점과 결제 지점의 OR 조회 범위, 최소 목록 필드, 서버형 `canEdit`, 입력·불변 필드·버전·멱등·CSRF·계정/소속 검사를 구현했다. 지연 및 JSON 본문 대기 이후에도 현재 계정·권한을 다시 검사한다.
- Backend SQL은 등록 지점이 null이어도 읽을 수 있는 지점에서 결제한 이력이 있으면 조회를 허용한다. 데모도 이 조건을 따르며, 결제 없는 미지정 고객의 OWNER/전체 지점 전용 사례를 별도로 검증했다.
- `MockStore`: 입력한 회원 정보는 메모리에 남기고 저장소에는 고정 fixture만 기록한다. canonical 생성 멱등 결과는 별도 메모리 WeakMap을 사용한다. 이전 버전의 회원 개인정보 스냅샷도 재직렬화에서 제거한다. MOCK 화면에 새로고침 시 변경 초기화 안내를 표시한다.
- 실서버 시험은 `npm run test:e2e:customers:live`로 분리했다. 기본 MSW 시험과 기존 초대 live 명령은 고객 시험을 자동 실행하지 않는다. 비밀번호·고객 요청 본문이 trace에 들어가지 않도록 live trace를 끈다.

## 5. 검증 결과

- 최종 `npm run check`: TypeScript·ESLint 통과, **33개 파일 / 245개 시험 통과**(기존 209개 + 고객 관련 36개).
- 고객 관련 36개: 모델 5개, 어댑터 2개, UI 12개, MSW 계약·권한·개인정보 16개, 저장소 개인정보 1개. 409·422·부분 PATCH·조회 실패·배경 오류 중 초안 보존·권한 회수·지연 응답·공유 결제 지점·검색 상한·개인정보 저장 방지를 포함한다.
- 새 고객 MSW Chrome 시험은 등록·수정·상태 변경, 실제 MSW HTTP 409, URL 복원·키보드 이탈 확인, 읽기 전용·타 지점 거절의 **4개를 우선 통과**했다.
- 기존 기능을 포함한 첫 Chrome 통합 실행은 31개 중 29개 통과했다. 나머지 두 개는 앱/MSW가 준비되기 전 시험 helper가 CSRF를 요청해 빈 프록시 응답을 JSON으로 읽은 문제였다. 고객 화면의 준비·접근 거절 표시와 기존 채팅 입력의 표시를 명시적으로 기다리도록 수정했다. 두 실패 사례만 재실행해 모두 통과했다. 애플리케이션의 오류 응답을 성공으로 바꾸지 않았다.
- 최종 `playwright test` 고객·상품·업무·채팅·workflows·extended·responsive·smoke **31개 모두 통과(2.7분)**. 고객 등록·권한·충돌과 기존 결제/환불·룸 예약·데모 DM·채팅 재전송·업무 완료·세 테마·1440/1024/390px 화면을 포함한다.
- `npm run test:builds`: live/demo 프로덕션 빌드 성공, 모드별 Chrome 시험 **2개 통과**. live 오류가 MSW·데모 로그인으로 대체되지 않음을 확인했다. Vite의 500kB 청크 크기 권고가 출력됐으며 빌드는 성공했다. 이번 범위에서 전체 번들 구조는 바꾸지 않았다.
- 1440px 고객 목록과 390px 회원 등록 폼을 직접 캡처·검토했다. 가로 넘침이 없고 입력·저장 버튼·포커스가 표시됨을 확인했다. 임시 캡처 실행 스크립트는 정리하고 이미지·로그는 무시되는 `qa-artifacts/`에 유지한다.

### 실제 Backend·별도 DB

Backend main `8eb2af6`을 무시되는 전용 디렉터리에 아카이브하고 Java 21로 `bootJar`를 새로 빌드했다. 기존 Backend 작업 트리의 `.env`나 오래된 jar는 사용하지 않았다. MySQL 8.4 전용 DB(`customer_live`, 13319), Backend(18089), Vite live(15179)를 사용했다. 공식 오프라인 `ownerBootstrap`과 전용 DB fixture로 OWNER·작성 직원·조회 직원을 준비했다.

- 실제 Chrome **4개 모두 통과(22.2초)**. MSW 없이 실행했다.
- OWNER 등록 → 새로고침 → 상세 → 메모 수정 → 사유를 포함한 상태 변경 → 다시 새로고침 후 값 유지.
- 서로 다른 OWNER·`members:write` 직원 세션의 실제 409. 초안 보존, 최신값 비교, 이름만 PATCH하고 다른 직원이 쓴 메모가 남음을 확인했다.
- 조회 직원에게 등록·수정 UI 비노출과 직접 변경 403, 타 지점 고객 상세 404 및 목록 total 0.
- 실제 서버 422는 한 번의 PATCH 연락처만 잘못된 값으로 바꿔 발생시켰다. 서버 필드 오류·입력 보존·수정 후 재시도를 확인했으며 가짜 오류 응답을 주입하지 않았다.
- 고객 이름·이메일·메모가 브라우저 저장소에 기록되지 않음을 확인했다.
- 실제 실행은 같은 전용 포트·프록시·Chrome·trace-off 설정의 ignored Playwright 설정을 사용했다. 전달용 tracked 설정의 `npm run test:e2e:customers:live -- --list`로 고객 시험 4개만 수집됨을 추가 확인했다. 기존 `test:e2e:live -- --list`는 초대 시험 4개만 유지한다.
- 실행한 Backend PID·포트와 생성 컨테이너의 ID·이름·포트를 대조한 뒤 해당 리소스만 종료·제거했다. 일회용 자격증명 fixture도 삭제했다. 사용자 DB·다른 서버·작업 트리는 변경하지 않았다.

## 6. 남은 작업 / 인수 구분

- #19의 목록·등록·수정·상태, URL/상한, 권한 버튼, 충돌·필드 오류, 개인정보 인수 조건은 위 시험으로 확인했다. 운영 HTTPS·SMTP·대량 검색 부하·다중 인스턴스 SSE는 이 검증 범위가 아니다.
- #20은 이번 정본 타입과 고객 조회 어댑터를 재사용하되, 결제 후 고객 조회 범위 확장과 이용권·결제 캐시 갱신을 함께 검증해야 한다. 기존 legacy 결제·좌석 데모 모델의 전면 교체는 하지 않았다.
- 고객 구매·사용 내역, 타 지점 요약, 병합, 개인정보 파기는 해당 후속 이슈에서 처리한다.
- 원격 main 갱신·PR 병합은 사용자가 수행한다. 브랜치 push·PR 준비 결과는 전달 기록에 추가한다.
