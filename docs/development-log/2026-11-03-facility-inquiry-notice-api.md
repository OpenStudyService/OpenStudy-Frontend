# 2026-11-03 시설·문의·공지 정본 API 연결 (#28)

## 1. 배경 / 문제

작업은 11월 2일 시작하여 11월 3일 검증했다. Frontend #28의 세 화면은 ResourcePage의 데모 DTO와 범용 명령을 사용했다. 루트 AGENTS.md, graphify 스킬·그래프, 이슈·현재 구현·관련 개발 기록을 확인했다. PR #59·#60이 병합된 최신 Frontend main `17522df`를 fetch하고 `feature/facility-inquiry-notice-api`를 만들었다.

Backend #74 계약과 #78·#79·#80의 종료 상태뿐 아니라 실제 코드와 main의 병합 커밋을 확인했다. 구현 PR #144(`898ba32`), #145(`7960667`), #146(`da1a05a`)은 Backend main에 포함돼 있다. `collaboration-api.md`와 기존 생성 DTO를 대조했다. 계약 충돌이나 별도 정책 결정이 필요한 항목은 발견하지 않았다.

기존 미추적 `.gitattributes`와 Backend의 환경 파일·다른 작업 변경은 수정하거나 커밋에 포함하지 않는다. Backend의 진행 중인 작업과 독립된 복사본으로 검증했다.

## 2. 검토한 선택지

- 범용 데모 폼을 유지하며 필드를 변환하는 방법과, 공통 UI를 재사용하면서 정본 DTO용 화면·폼을 분리하는 방법을 검토했다. 시설의 열린 점검 작업, 문의의 최소 고객 정보·이력, 공지의 다중 대상 지점을 기존 단일 상태·단일 지점 모델로 표현하기 어려워 후자를 선택했다.
- 수정 충돌에서 모든 필드를 다시 보내는 방법은 다른 편집자의 변경을 덮어쓸 수 있다. 최초 조회와 초안을 비교해 사용자가 변경한 필드만 PATCH하고, 명시적으로 확인한 최신 버전을 사용하기로 했다.
- 실제 검증은 기존 개발 DB를 사용하지 않고 Backend의 커밋을 별도 추출한 서버와 일회용 MySQL을 선택했다.

## 3. 결정 및 이유

- ResourcePage·RecordPanel의 진입점을 전용 화면으로 연결하고 Panel, Heading, Badge, Field, Pager, ErrorState, 기존 고객 검색을 재사용했다. Panel의 동기 `onOpenAutoFocus` 처리는 변경하지 않았다.
- API는 `foundation.generated.ts`의 DTO와 Backend의 한글 상태·정본 경로를 따른다. 성공 응답도 런타임 검증하여 잘못된 데이터로 성공을 보고하지 않는다. live에 Mock 원장을 가져오거나 실패를 데모 데이터로 대체하지 않는다.
- 생성·점검 완료만 멱등 키를 보내고 동일 입력 재시도는 같은 키를 유지한다. 수정·상태 변경·답변은 조회 버전을 보낸다.
- 상세의 `canEdit`, `canComplete`, `canChangeAssignee`와 현재 지점 권한을 사용한다. 전체 공지 작성은 OWNER만 가능하고, 지점 대상은 쓰기 권한이 있는 지점만 선택할 수 있다. 서버가 최종 권한을 다시 검사한다.
- 권한 문맥·지점·상세 변경은 폼을 분리하고 진행 중 요청을 취소한다. 403에서는 세션을 재조회한다. 접근 오류가 난 상세는 이전 캐시 대신 오류를 표시한다.
- 실제 연속 명령 시험에서 저장 직후 과거 상세 버전으로 다음 명령이 나가는 경합을 확인했다. 성공 응답을 상세 캐시에 먼저 넣고, 이전 GET을 취소한 뒤 목록·상세·집계를 무효화하도록 보완했다.

## 4. 구현 내용

- 시설 목록·상세·등록·수정, 유형 조회와 OWNER의 유형 추가, 담당자·열린 작업 처리 상태·시설 상태, 결과 필수 점검 완료, 마지막 결과·다음 점검일과 집계를 연결했다.
- 문의 목록·상세·대리 등록·담당자 변경·상태 변경·답변·페이지별 이력과 미처리 집계를 연결했다. 고객 ID 직접 입력은 없고 허용된 고객 검색 또는 지점별 정본 정확 일치 조회 결과만 선택한다. 검색어 변경·이탈 후 과거 정확 조회 응답은 취소·무시한다.
- 공지 목록·상세·등록·수정·고정·게시·게시 종료와 다중 지점 대상을 연결했다. 공개 범위와 고정 우선 정렬은 서버의 페이지 순서를 사용한다. 관리 권한 없는 직접 등록 주소도 차단한다.
- 저장 오류에서 입력을 유지하고 422 필드 오류를 표시한다. 409에서 최신 상세·버전을 비교하기 전에는 재저장을 막는다. 동기 잠금으로 중복 제출을 차단한다.
- MSW는 기존 데모 원장에 정본 메타데이터를 보존하는 어댑터를 사용한다. 정확 조회 증거는 현재 Mock 원장·직원·지점별로 분리하며 고객 조회 범위를 넓히지 않는다. live 빌드에는 포함되지 않는다.
- 모바일 목록은 내부 가로 스크롤로 표를 읽을 수 있도록 최소 너비를 둔다.

### 실행 구분

- 실제 서버: Backend main `9f06eea95f2a5019f3f4e9748bcaf21ddbf6b9f9`의 별도 복사본, 일회용 MySQL `collaboration_live`, Service Worker 없는 Chrome의 6개 시나리오를 통과했다. 두 OWNER 세션의 실제 409, 422·필드 보존, 실제 커밋 이후 응답 유실과 같은 키 재시도, 역할별 공개 범위·권한 회수를 포함한다.
- MSW·컴포넌트: 정본 DTO·재시도·두 상태·집계·문의 이력·공지 공개/정렬·정확 조회 증거, 초안 보존·필드 오류·중복 제출·늦은 응답·권한 회수·과거 GET 취소를 검사했다. 집중 검사 3개 파일 14개 통과. 이는 실제 DB 테스트와 다르다.
- `npm run check`: typecheck·lint, Vitest 전체 53개 파일 434개, 메일 도구 9개, 빌드 가드 19개 통과 후 과거 GET 취소·Mock 정확 조회 회귀 2개를 추가했다. 마지막 통합 실행 결과는 아래에 추가 기록한다.
- live/mock 빌드와 산출물 오염 검사, Chrome 산출물 검사 5개 통과. 기존 500KB chunk 경고는 남는다. 최종 코드 검사 결과는 아래에 누적한다.
- 첫 전체 검사는 기존 SSE 프록시 테스트 3개가 샌드박스 loopback EACCES로 실패했다. 로컬 통신이 허용된 환경에서 재실행해 통과했다. 실제 DB 첫 시작은 DB 준비 타이밍으로 실패하여 동일 컨테이너의 준비 상태 확인 후 재시작했다.

## 6. 남은 작업 / 보류 사항

- 운영 배포·부하·실제 모바일 기기·다중 인스턴스, Backend 자체 통합 테스트 재실행은 수행하지 않았다.
- 채팅 독립 읽음(Backend #155·Frontend #27 후속)은 변경하지 않았다.
- main 직접 push·PR 병합·자동 병합은 하지 않는다. 작업 브랜치 push·PR 생성·CI 확인 후 사용자 병합을 기다린다.
