# 2026-11-05 초대 수락 링크 수명 수정·Frontend #6 종료 검증

## 1. 배경 / 문제

[Frontend #6](https://github.com/OpenStudyService/OpenStudy-Frontend/issues/6)의 실제 서버·메일 더블·두 브라우저 검증 항목은 10월 27일 이후 미완료로 남아 있었다. 이후 PR #17의 실제 Mailpit 연동과 PR #51의 열린 상세 갱신이 병합됐으므로 최신 main에서 다시 확인했다. 이전 개발 기록을 덮어쓰지 않는다.

Frontend main `a863cbf` 기준 별도 작업 트리에서 시작했다. Backend는 원본 작업 트리·환경 파일 대신 별도 clone의 main `aa2ebc8`을 빌드했다. 처음에는 검증 브랜치였지만 실제 회귀에서 수락 화면의 토큰 손실을 발견해 `fix/invitation-link-lifecycle`로 변경했다. Backend 소스는 수정하지 않았다.

## 2. 검토한 선택지

- 과거 PR의 성공 기록만으로 미완료 체크를 정리하는 대신 최신 코드·실제 서버로 재검증했다.
- 기존 `location.hash || location.key`를 폼 key로 쓰면 URL에서 토큰을 지운 뒤 브라우저 이력이 동기화될 때 key가 바뀌어 폼이 다시 만들어진다.
- `location.key`만 쓰면 같은 history entry에서 다른 fragment 링크를 열 때 이전 폼을 재사용할 수 있다. URL 정리와 새로운 링크 진입을 구분해야 한다.

## 3. 결정 및 이유

현재 경로의 이력 key·마지막 관찰 fragment·초기 fragment·숫자 revision을 컴포넌트 메모리에만 둔다. 같은 entry의 fragment 제거는 폼을 유지하고, 새 entry 또는 새로 들어온 fragment는 폼을 새로 만든다. 같은 링크를 다시 열어도 서버에서 다시 검증한다.

토큰을 URL·브라우저 저장소·Query 캐시로 되돌리지 않는다. React 폼 key도 토큰 대신 숫자 revision을 쓴다. 기존 POST preview/accept·CSRF·신규/기존 계정 계약을 그대로 사용한다.

## 4. 구현 및 시험 보강

- 수락 폼이 URL 정리 후 이력이 동기화돼도 토큰과 입력을 잃지 않도록 수정했다.
- 새 fragment와 같은 링크 재진입은 이전 입력을 버리고 새 preview를 요청하는 단위 회귀를 추가했다.
- 실제 Chrome에서도 비밀번호 입력 후 정리된 URL의 이력 동기화 이벤트를 발생시켜 수락이 계속되는지 확인한다. 성공 API를 fixture로 대체하지 않는다.
- 관리자 상세를 열어 둔 상태에서 실제 Mailpit 링크를 수락하면 승인 버튼과 최신 version이 갱신되는지 확인한다. 관리자 DTO 비밀 필드 검사는 응답 원문 대신 boolean만 검사한다.
- 같은 직원의 추가 지점·소속 회수·같은 지점 재초대 복구와 기존 지점 접근 유지를 실제 API로 검증한다. 수신함의 과거 링크를 하나가 아닌 집합으로 제외해 세 번째 메일을 정확히 기다린다.
- 샘플 API를 끄고 실제 지점 fixture와 보호된 `/tasks`의 200/403으로 업무 진입을 검증한다. 미구현 M9 홈 요약을 성공으로 대체하지 않는다.
- 재사용 가능한 별도 mock Playwright 설정과 명령을 추가해 기존 서버 재사용으로 다른 코드를 검증하지 않도록 했다.

## 5. 검증 결과

### 실패·재현과 수정 결과

- 첫 실제 서버 실행: 3개 통과, 반려 시나리오의 신규 수락 1개 실패. 폼이 `유효한 이메일 초대 링크를 다시 열어 주세요` 상태가 됐다. 반려 단독 재실행은 통과했으므로 최초 실패를 통과로 집계하지 않는다.
- 브라우저 이력 동기화로 같은 토큰 손실을 단위 시험에서 결정적으로 재현했다. 수정 전 기존 5개 통과/신규 1개 실패, 수정 후 7개 모두 통과했다.
- 수정 후 실제 Backend·MySQL·SMTP worker·Mailpit·Google Chrome: 최종 4개 모두 통과(50.9초). 원문 메일에서 얻은 링크와 서로 다른 브라우저 세션을 사용했다.
- 수정 후 mock Chrome: 2개 통과. 실제 SMTP 검증과 별도다.

- 최종 `npm run check`: TypeScript·ESLint, Vitest 69파일/564개, 실메일 도구 자체 시험 9개, 빌드 가드 19개 모두 통과. 도구 시험은 외부 메일 수신 성공이 아니다.
- 최종 `npm run test:builds`: live/mock 빌드·모드 격리 검사 및 Chrome 산출물 5개 통과.
- `graphify update .`: AST 2,589노드/7,780간선 갱신, LLM/API 비용 없음. 기존 ignore 정책에 따라 로컬 지도만 유지한다. 미설치 SQL parser와 심볼을 모델링하지 않는 설정 파일 경고는 실행 시험과 구분한다.
- 재현 환경: Frontend `a863cbf` 기반 작업 브랜치, Backend main `aa2ebc8` 별도 사본, JDK 21, MySQL 8.4.11(`invitation_live`, 13346), Mailpit v1.27(loopback SMTP 11025/API 18025), 실제 Backend 18086, live Vite 15176, mock Vite 15179, Google Chrome. 원본 `.env`를 복사하거나 읽지 않았다.
- 종료 시 jar 경로·PID와 전용 컨테이너 전체 ID를 확인해 검증 서버·MySQL/Mailpit·익명 볼륨을 제거했다. 별도 Backend 사본 삭제와 두 전용 컨테이너 부재를 확인했다. 원래 Frontend의 `.gitattributes` 변경을 보존했다.
