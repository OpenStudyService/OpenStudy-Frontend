# 직원 상세에서 연속 저장 후 발생하는 잘못된 버전 충돌 수정

## 배경 / 문제

B06 운영 API와 F02 화면을 연결한 실제 브라우저 검증에서, 한 지점의 소속을 연속 저장한 다음 계정을 제한하면 같은 상세 화면에서 수행한 변경인데도 409가 발생했다. 계정 폼과 각 소속 폼이 직원 버전을 처음 한 번만 보관해, 형제 폼의 성공한 저장으로 증가한 직원 버전을 알지 못했다. 다른 지점 소속을 이어 저장해도 같은 문제가 발생할 수 있었다.

## 검토한 선택지

폼을 새 버전마다 다시 마운트하거나 props 변경에 맞춰 모든 상태를 갱신하면 다른 폼의 미저장 이름·상태·권한 입력을 잃을 수 있다. 조회 결과의 최신 버전을 무조건 공유하면 외부 사용자가 수정한 내용을 아직 비교하지 않은 폼이 충돌 없이 덮어쓸 수 있다.

## 결정 및 이유

직원 상세가 계정 폼과 각 소속 폼의 버전 기준을 따로 관리한다. 성공한 저장 응답을 받으면 해당 요청이 사용한 직원 버전과 기준이 같은 형제 폼만 다음 직원 버전으로 전진시킨다. 소속별 버전은 각 소속에 유지한다. 외부 충돌의 명시적 최신 확인은 그 폼만 갱신한다. 따라서 버전 조회나 다른 폼 저장 때문에 초안 입력을 바꾸지 않으며, 실제 외부 충돌을 건너뛰지 않는다.

## 구현 내용

- 소속 저장 성공을 계정 폼과 다른 지점 소속 폼에 전달하고, 계정 저장 성공도 소속 폼에 전달한다.
- 외부 충돌 후 한 폼이 새 버전을 확인·저장해도 오래된 다른 폼의 기준은 자동으로 따라가지 않는다.
- 최신 확인에서 새 소속이 발견되면 새 폼은 해당 조회 결과로 기준을 초기화한다. 기존 폼의 오래된 기준은 유지한다.
- 이름·상태·권한·프리셋 초안은 기존 로컬 상태로 유지하며 effect나 재마운트를 사용하지 않는다.

## 검증 결과

- TypeScript·ESLint·전체 단위 테스트 86개와 live 빌드 통과.
- 추가 회귀 5개: 소속 2회 저장 후 미저장 계정 저장, 지점 A 저장 후 미저장 지점 B 저장, 계정 저장 후 미저장 소속 저장, 외부 수정 후 형제 폼의 명시적 확인·저장에도 계정 409와 입력 보존, 새 소속 발견 후 초기 버전과 기존 폼의 충돌 보존.
- 버전을 검사하는 상태 있는 API 더블로 실제 성공/409 조건을 검증했다. 이 기록의 자동화 검증은 실제 서버 재검증과 구분한다.
