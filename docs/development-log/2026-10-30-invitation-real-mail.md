# 실제 수신함 초대 검증 준비와 열린 상세 상태 갱신

관련 이슈: [Frontend #6](https://github.com/OpenStudyService/OpenStudy-Frontend/issues/6), [Backend #14](https://github.com/OpenStudyService/OpenStudy-Backend/issues/14), [Backend #18](https://github.com/OpenStudyService/OpenStudy-Backend/issues/18).

## 1. 배경 / 문제

기존 초대 화면과 실제 Spring·MySQL·Mailpit 검증은 병합되어 있다. 사용자는 실제 외부 이메일 수신까지 검증하기 위해 프론트는 이 작업에서, SMTP 등 백엔드는 Claude Code에서 진행하기로 했다. 작업 시작 시 프론트·API 주소와 테스트 수신 이메일은 아직 준비되지 않았다고 확인했다. 따라서 이번 변경의 완료 범위는 실메일 검증 도구·절차 준비와 관련 UI 결함 수정이다. 외부 메일 수신 성공으로 보고하지 않는다.

`main`의 `9faba44`에서 `feature/invitation-real-mail`을 만들었다. 사용자의 미추적 `.gitattributes`는 작업에 포함하지 않는다. 사용자 요청에 따라 실메일 검증 도구와 초대 UI 검토·수정을 서브에이전트가 나누어 수행했고, 부모가 통합 검토·문서·최종 검증을 맡았다.

## 2. 검토한 선택지

- 기존 Mailpit suite의 수신함·DB 주소를 외부 서비스로 바꾸는 방법은 기존 만료 시험의 DB 변경과 임의 `.test` 수신 주소 생성까지 실제 환경으로 가져오게 된다. 기존 자동 회귀를 보존하고 별도 명령을 제공하기로 했다.
- 실제 수신함 API 자동 접근은 제공자와 접근 계약이 없는 상태다. 도구가 수신함 비밀번호나 메일 토큰을 받는 대신 운영자가 실제 받은 링크를 임시 직원 브라우저에서 열고, 도구가 이후 API·화면 순서를 관찰하도록 했다.
- UI 검토에서 선택한 초대 객체를 목록에서 복사해 보관하는 구조가 확인됐다. 목록이 SSE로 갱신돼도 열린 상세에는 이전 발송 상태·수락 상태·버전이 남아 최종 승인 버튼이 나타나지 않았다. 목록의 객체 복사를 유지하는 대신 선택 ID별 상세 query를 기존 무효화 범위에 연결했다.

## 3. 결정 및 이유

별도 신규 계정 smoke는 관리자·직원을 분리된 임시 Chrome context로 연다. 운영자가 로그인·생성·수락·승인·재로그인을 직접 수행하고 도구는 지정 이메일·지점과 응답 순서를 확인한다. 프론트는 기존 same-origin `/api` 계약을 사용한다. SMTP 비밀값·발신 설정은 백엔드가 담당한다.

테스트 도중 다른 주소로 발송하거나 실수로 반복 생성하지 않도록 지정 수신 주소로 향하는 초대 생성 시도 한 번만 허용한다. 발송 결과가 불명확하면 자동 재시도하지 않는다. 이는 생성 요청의 제한이며 백엔드 worker의 재시도에 따른 실제 메일 도착 횟수를 보장하지 않는다. 재발급·반려·기존 계정 추가 지점 검증은 별도 수동 체크리스트로 명시했다.

상세 query에는 사용자·지점 범위·초대 ID를 포함한다. 기존 SSE의 query 무효화를 재사용하며, 연결이 없을 때도 명시적으로 상태를 조회할 수 있다. 재조회 중·실패 시 처리 버튼은 비활성화하고 409 후 최신 조회에서도 반려 사유를 보존한다.

## 4. 구현 내용

- `scripts/invitation-real-mail.ts`와 `test:e2e:real-mail`: 설정 검증, 두 임시 브라우저, 한 번의 지정 초대 생성, 실제 링크 수락·제한 세션·승인·재로그인 순서 관찰. 제한 세션의 업무 요청 403과 재로그인 후 200을 확인한다.
- `scripts/invitation-real-mail.test.ts`와 `test:real-mail:tool`: 설정·대상·중복 생성·잘못된 순서·타 지점·재로그인 누락에 대한 도구 회귀. SMTP 발송 시험으로 집계하지 않는다.
- 초대 상세 전용 GET, SSE 연동·수동 새로고침, 최신 상태·버전으로 명령, 반려 입력 보존, 다른 상세의 늦은 응답 분리.
- [실메일 실행 방법](../testing/invitation-real-mail.md), 기존 Mailpit 문서와의 구분, 백엔드 준비 조건과 추가 수동 시나리오.

## 5. 검증 결과

- 수정 전 새 상세 갱신 회귀를 실행해 기존 결함을 확인했다: 1 실패·3 통과. 수정 후 초대 관리 5개·수락 5개, 총 10개 통과. 열린 상세의 수락·발송 변경, 409 후 반려 사유·최신 버전 사용, 다른 초대로 이동한 뒤 늦은 이전 응답을 확인했다.
- 최초 `npm run check`는 타입·Lint 성공, 기존 SSE proxy 시험 3개가 localhost 소켓 `EACCES`로 실패하고 나머지 242개는 통과했다. 환경 권한 실패를 성공으로 표시하지 않는다.
- 최종 `npm run check`: TypeScript·ESLint, Vitest 33개 파일의 **248개**, 도구 node:test **9개** 모두 통과. 기존 SSE proxy 소켓 시험은 정상 네트워크 권한으로 다시 실행해 통과했으며 제품 코드를 바꾸어 우회하지 않았다.
- `npm run build`: live 빌드 성공. 500 kB 초과 청크 경고는 남아 있으며 이번 변경의 기능 실패는 아니다.
- `npm run test:e2e:real-mail -- --help` 성공. 설정 없는 실행은 브라우저를 시작하거나 메일을 보내지 않고 값이 없는 오류 코드와 함께 exit 1을 반환하는 것을 확인했다. 도구 스크립트의 독립 TypeScript·Lint도 통과했다.
- Chrome 초대 회귀 **2개 통과**: 신규 수락·승인 후 재로그인, 누락·만료 fragment 및 query token 미전송. 처음에는 기본 설정이 기존 5173 서버를 재사용해 데모 버튼·mock 오류 문구를 찾지 못하고 2개가 실패했다. 기존 서버를 종료·변경하지 않고 임시 설정의 별도 15179 포트에서 새 mock 서버를 띄워 두 시나리오를 통과했다. 임시 설정은 제거했다. 이 결과는 MSW 기반이며 실제 SMTP 시험이 아니다.
- `git diff --check`, `graphify update .` 완료. graphify는 1,335 nodes·4,028 edges로 갱신했으며 추적하지 않는 로컬 그래프를 커밋하지 않았다. 파서가 모델링하지 않는 파일 경고는 실행 검증과 구분한다.
- 독립 서브에이전트가 변경을 읽기 전용으로 검토했고 차단할 구체 결함을 발견하지 못했다. 새 도구의 Chrome 관찰 루프 전체·실제 Backend·외부 이메일 수신은 미실행이다. 순수 도구 회귀 9개를 실메일 성공으로 집계하지 않는다.

## 6. 남은 작업 / 보류 사항

- 실제 프론트·API URL, 관리 계정·테스트 지점, 미가입 테스트 수신 주소와 Backend #14의 SMTP 발송 설정이 필요하다. 현재 미제공으로 외부 이메일 수신·실제 서버 결합은 새로 검증하지 않았다.
- 환경 준비 후 신규 초대의 실제 수신함 도착·스팸 여부를 확인하고 smoke를 실행한다. 기존 직원·재발급·취소·만료·반려는 문서의 별도 시나리오로 확인한다.
- 운영 HTTPS·쿠키·CSRF·SSE·프로세스 복구와 Backend #18 전체 인수는 이 PR의 완료 범위가 아니다. Frontend #6을 자동 종료하지 않는다.
- 권한 프리셋 등록의 멱등 키 누락과 비밀번호 초기화·잠금 해제는 이번 작업에 포함하지 않았다.
- 작업 브랜치 구현·검증·커밋과 push·PR까지 준비하고, 원격 main 반영과 병합은 사용자가 수행한다.
