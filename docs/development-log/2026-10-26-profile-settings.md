# 본인 닉네임 화면의 실제 API 연결 (#13)

## 배경 / 문제

기존 설정은 nickname과 avatar를 함께 전송하고 계정 version을 보내지 않아, Backend PR #30으로 병합된 닉네임 API에서 거부됐다. 상단 사용자 메뉴도 이름만 표시해 닉네임 저장 결과를 확인할 수 없었다.

Frontend [#13](https://github.com/OpenStudyService/OpenStudy-Frontend/issues/13), Backend [#27](https://github.com/OpenStudyService/OpenStudy-Backend/issues/27)·[PR #30](https://github.com/OpenStudyService/OpenStudy-Backend/pull/30), 관련 직원 상세 버전 공유 PR #12와 기존 조직·세션 개발 기록을 확인했다. Backend #27의 서버 인수 조건은 완료로 체크하고 브라우저 후속 검증을 구분했으며, #13에는 서버 계약이 준비됐음을 반영했다. Frontend main `2417d4a`에서 `feature/profile-settings`를 생성했다. 작업 전 프론트 작업 트리는 깨끗했다. 별도 문서 PR #14는 기능 구현과 중복되지 않아 이 브랜치에 포함하지 않았다.

## 검토한 선택지

- 일반 ResourceForm을 계속 사용하면 본인 계정 version 유지·명시적 충돌 복구·성공 응답으로 세션 갱신을 위한 기능을 범용 폼에 추가해야 했다. 기존 프로필 카드 배치를 유지하는 전용 ProfileForm으로 해당 상태만 관리한다.
- 저장 뒤 GET /me만 무효화하면 후속 조회 실패로 저장 여부가 불분명해지고 사용자가 성공한 서버 정규화 값을 즉시 보지 못한다. PATCH 성공의 CurrentUser를 그대로 세션 캐시에 반영한다.
- 세션이 갱신될 때 폼 version까지 자동 갱신하면 작성 중 관리자 편집을 덮어쓸 수 있다. 폼의 최초 version은 유지하고 본인 저장 성공 또는 사용자의 명시적 최신 정보 확인에서만 전진시킨다.

## 결정 및 이유

Backend OpenAPI 0.1.3-profile이 정본이며 `ProfileUpdate`와 `CurrentUser` 생성 타입을 직접 사용한다. 공통 api의 쿠키·CSRF·401 처리와 조직 화면 SaveError의 충돌 안내를 재사용한다. 실패 입력은 로컬 폼에 유지한다. 사용자 변경 시에만 폼을 교체하고, 배경 세션 재조회로 폼을 초기화하지 않는다.

M1 요청은 nickname/version만 허용한다. 이메일은 읽기 전용이며 기존 avatar 표시만 유지한다. 이미지 선택·변환·전송을 제거하고 사진 변경은 후속 제공 안내로 분리했다. 실제 업로드 구현은 M14 범위다.

## 구현 내용

- 닉네임 1~100자 검증, version 포함 PATCH, 전송 중 중복 저장·입력 변경 방지와 필드 오류 연결을 구현했다. 공통 오류 표시에 한국어 필드명을 선택적으로 제공해 기존 화면 동작을 유지한다.
- 성공 응답의 닉네임/version을 폼과 세션 캐시에 반영하고 직원 조회 캐시를 stale로 표시한다. 상단 사용자 메뉴·아바타는 닉네임을 우선 표시하며 값이 없으면 이름을 쓴다.
- 성공 응답 적용 전 진행 중 세션 조회를 취소하고, 로그아웃·사용자 변경 이후 도착한 응답이 세션을 복원하지 못하도록 취소 신호·현재 사용자 ID를 검사한다. 승인 제한·계정 제한 상태에는 저장을 허용하지 않으며 403에서는 기존 세션 조회로 현재 권한을 재확인한다.
- 409에서는 입력과 최초 version을 유지하고 최신 정보 확인 시 서버 닉네임·이름·version을 보여 준다. 자동 재전송하지 않으며 사용자가 다시 저장해야 한다. 422·네트워크·서버 실패에서 성공 안내를 표시하지 않는다.
- MSW도 nickname/version만 수용하고 보호 필드를 거부하며, account version 증가·시간·409의 latestVersion/reloadUrl을 실제 계약과 맞췄다. 이 동작은 브라우저 시연이며 서버 보안을 대체하지 않는다.
- `npm run api:foundation`, `npm run api:generate`로 두 기존 생성 경로의 타입·프로필 계약을 동기화했다. 과거 전체 화면 계약에 누락되어 있던 소속의 선택적 status/version도 현재 생성 원본대로 반영됐다.
- graphify AST 탐색 자료를 생성·갱신했다. 프론트에 기존 커밋된 그래프는 없었다. 새 로컬 산출물은 `.gitignore`에 두어 Vite/Tailwind가 분석용 HTML까지 제품 스타일 원본으로 스캔하지 않도록 했다. 그래프를 재생성하는 규칙은 유지한다.

## 검증 결과

### 자동 검사와 MSW

- Node.js 24.19.0, `npm run check` 통과: TypeScript, ESLint, Vitest 116개/14개 파일, 실패·건너뜀 0. `npm run build`의 live 배포 빌드 통과.
- 첫 전체 시험은 프로필 UI 8개가 실패했다. 관찰자가 없는 테스트용 세션 캐시를 gcTime=0으로 즉시 제거한 설정과 재렌더 시 StrictMode 래퍼를 바꾼 테스트를 수정했다. 실제 Layout은 세션 쿼리를 구독한다. 수정 후 관련 26개 및 최종 전체 116개를 통과했다. 초기 실패를 성공으로 기록하지 않는다.
- UI 단위 시험: 3역할의 nickname/version 전송·서버 정규화 결과·연속 저장 version, 보호 필드 미전송·사진 표시/입력 제거, 422/500/네트워크 입력 보존, 배경 조회 후 진짜 409, 명시적 최신 조회·재저장, 제한 세션, 403 재확인 및 늦은 응답의 세션 복원 방지를 확인했다.
- MSW HTTP 계약 시험: 3역할 저장·version 증가·이메일 유지·충돌 메타데이터, 이메일/사진/ID/권한/상태 필드 및 잘못된 닉네임 거부를 확인했다.
- Chrome Playwright `tests/profile.spec.ts tests/smoke.spec.ts`: 프로필 저장·표시·새로고침, 외부 변경 409·입력 보존·재저장 및 기존 전체 OWNER 화면 smoke 3개 통과.

### MSW를 끈 실제 Backend·MySQL·Chrome

Backend main `3cc84b6`의 실제 API를 Java 21.0.12.1, 별도 profileverification 프로필로 실행했다. MySQL 8.4.11 고정 이미지 `mysql@sha256:24989179f58856db763f418010c1169fecc944e3ec1ea7e921572d83eb070f70`의 일회용 DB를 localhost 임의 포트에 만들고 V1~V3 migration을 적용했다. OWNER는 별도 ownerBootstrap 명령으로 생성했다. MANAGER·STAFF·PENDING 직원과 소속은 해당 DB의 검증용 SQL로 준비했으며 초대·메일 검증으로 간주하지 않는다. 사용자 DB는 사용하지 않았다.

- 실제 Chrome에서 OWNER·MANAGER·STAFF 각각 저장 → 상단 메뉴·프로필의 서버 값 일치 → 새로고침 → 로그아웃·재로그인을 확인했다. 브라우저에 MSW service worker 등록이 없음을 확인했다.
- 전송한 본문 키는 nickname/version 두 개뿐이며 이메일·avatar·직원 ID·권한·scope를 보내지 않았다. 서버가 앞뒤 공백을 제거한 응답이 폼과 헤더에 반영됐다.
- MySQL에서 이메일·역할·소속·권한 보존, 닉네임·계정 version·updated_by 및 UPDATE_PROFILE 감사 기록을 확인했다. 프로필 저장으로 소속 version은 증가하지 않았다.
- 두 독립 Chrome context의 같은 직원 편집에서 첫 저장 200·두 번째 409를 확인했다. 실패 화면에 요청 ID와 원래 입력이 남고, 최신 서버 닉네임 확인 후 명시적 재저장이 성공했다.
- 유효 UI 입력을 브라우저 전송 단계에서 101자로 바꾸는 요청 주입으로 실제 서버 422를 발생시켰다. 한국어 닉네임 필드 오류·aria-invalid·입력 보존·성공 안내 미표시를 확인했다. 정상 요청이 잘못된 길이를 보냈다는 의미는 아니다.
- 잘못된 CSRF 헤더를 전송하는 주입에서 실제 서버 403을 확인하고 입력을 보존했다. 이후 원래 요청으로 재시도하면 공통 클라이언트가 새 토큰을 받아 200으로 저장했다.
- 503 응답과 네트워크 실패는 브라우저에서 의도적으로 주입하여 입력 보존·성공 미표시를 확인했다. 실제 서버가 자발적으로 503을 발생시킨 검증과 구분한다.
- 실제 OWNER 계정 제한 API로 STAFF를 제한한 뒤 기존 직원 화면의 저장 시도가 로그인으로 이동하고 개인 폼을 제거했다. 실제 APPROVAL_ONLY 로그인 및 설정 직접 진입도 승인 화면으로 이동하여 닉네임 저장을 제공하지 않았다.
- 390px 모바일에서 프로필 폼·저장 버튼을 확인했고 가로 넘침이 없었다. 데스크톱·모바일 및 오류 화면을 렌더 확인했다. 제작·검증 스크립트, JSON·스크린샷은 저장소 밖 `outputs/frontend-13-profile/`에 보관한다.

`git diff --check` 통과. 직접 실행한 프론트·백엔드 서버와 일회용 DB 컨테이너는 검증 종료 후 정리했다.

## 남은 작업 / 보류 사항

- 사진 업로드·파일 검증, 비밀번호·테마 서버 저장은 이번 범위가 아니다.
- 공통 lookups·SSE 서버 미제공 안내는 기존 동작이다. 열린 SSE 회수·프록시/TLS·전체 초대/메일/상품 흐름은 기존 Backend #17/#18에서 계속 검증한다. 이번 프로필 결과로 전체 M1 또는 통합 검증 #18의 모든 조건을 완료했다고 표시하지 않는다.
- Backend #27에는 실제 프로필 브라우저 인수 결과를 연결한다. Frontend는 작업 브랜치 push·PR로 제공하고 main 반영·PR 병합·자동 병합은 하지 않는다. 병합은 사용자가 수행한다.
