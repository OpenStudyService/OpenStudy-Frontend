# 2026-11-13 · 상품·입퇴실 이력·출퇴근 목록 화면 공통 레이아웃 적용

관련 이슈: [#109](https://github.com/OpenStudyService/OpenStudy-Frontend/issues/109) · 선행 작업: [#106 기록](2026-11-13-unify-list-layout.md), PR #114

## 1. 배경 / 문제

#106에서 회원 목록 형태를 `src/shared/ui/ListLayout.tsx`(`ListCard`, `ListFilters`, `ListTable`, `ListFooter`)로 뽑고 보유 이용권·결제 관리에 적용했다. 남은 목록 화면은 형태가 여전히 달랐다.

- **상품 목록**: 표가 아니라 상품마다 테두리 카드(`article`)를 쌓은 목록이었다. `상품 등록`은 제목 옆, 필터는 라벨 달린 `Field` 4열 그리드와 그 위의 별도 `판매 가능 여부` 필터였다. 상세는 `상품 상세: {name}` 버튼, 페이지는 `organization/shared`의 `Pager`였다.
- **입퇴실 이력**: 라벨 달린 `Field` 필터, 3열 기간 폼, 표 밖 로딩·오류·빈 상태, `SalesPager`, 마지막 열의 `상세` 버튼이었다.
- **출퇴근·휴게**: `aria-label` select였지만 카드 없이 `label` 감싼 필터 줄, 표 밖 `DataNotice`, 표 아래 문단으로 된 빈 상태, `이전 · N페이지 · N건 · 다음` 순서의 자체 페이저였다. 상세는 출근 시각 버튼으로 열었다.

## 2. 검토한 선택지

- **입퇴실 이력 기간 조회 위치**
  - 필터 바에 넣기(결제 관리와 같은 방식): 결제 기간은 즉시 반영되는 `date` 두 칸이지만, 입퇴실 이력은 초 단위 `datetime-local` 두 칸과 `기간 적용`·`전체 기간` 버튼을 가진 제출형 폼이다. 1440px에서도 필터 바가 두 줄로 넘어가고, 즉시 반영 select와 제출형 입력이 한 줄에 섞인다.
  - 필터 바 바로 아래 카드 안 한 줄(보유 이용권의 고객 선택 행과 같은 보조 행)에 두기: 즉시 반영 필터와 제출형 기간 조회를 구분할 수 있고 기존 적용 방식을 그대로 둔다.
- **`RangeFilter` 처리**: `CustomerHistory`(이용권 구매·사용 내역 패널)도 같은 컴포넌트를 쓴다. 입퇴실 이력 전용 폼을 새로 만들면 검증·적용 로직이 두 벌이 되므로, `inline` 옵션만 추가해 배치만 바꾸기로 했다.
- **상품 상세를 URL로 옮길지**: 다른 목록처럼 `detail` 파라미터로 옮기면 새로고침·링크 공유가 가능해진다. 하지만 `ProductDetail`이 목록 행의 `Product` 객체를 그대로 받아 쓰므로, URL로 옮기려면 단건 조회 흐름과 그 오류·권한 처리를 새로 넣어야 한다. 배치 통일 범위를 넘어선다.

## 3. 결정 및 이유

- 세 화면 모두 #106 재사용 방법 1~5단계를 그대로 따랐다. `ListLayout`은 수정하지 않았다. 세 화면에 필요한 배치가 기존 props로 모두 표현됐다.
- **기간 조회는 카드 안 보조 행**으로 두고 `RangeFilter`에 `inline` 옵션을 추가했다. 기본값은 기존 3열 그리드라 `CustomerHistory`는 그대로다. `inline`에서도 입력의 접근성 이름(`조회 시작 (한국 시각, 포함)` 등)은 유지했다.
- **390px 기간 입력 줄바꿈**(#106 보류 항목): 그냥 감싸 두면 시작 입력, `~`, 종료 입력이 폭에 따라 들쭉날쭉 줄바꿈된다. 그래서 `sm`(640px) 미만에서는 `조회 기간` 문구·시작·종료를 각각 한 줄 전체 폭으로 쌓고 `~`를 숨겼다. `sm` 이상에서는 한 줄로 둔다. 출퇴근·휴게의 `출근일` 기간 입력에도 같은 규칙을 적용했다. 결제 관리 기간 입력은 이번 대상 화면이 아니어서 바꾸지 않았다.
- **`SalesPager` 제거**: 입퇴실 이력을 `ListFooter`로 바꾼 뒤 남은 사용처가 없어서(`src`·`tests` 검색) `payments/shared.tsx`에서 지웠다. `organization/shared`의 `Pager`는 다른 화면이 계속 쓰므로 수정하지 않았다.
- **상품 상세는 URL로 옮기지 않았다.** 기존처럼 `useState`로 선택 상품을 관리하고, 진입점만 상품명 셀 링크로 바꿨다(2절 이유).
- **상세 셀 링크 위치**: 상품은 상품명, 입퇴실 이력은 고객 이름, 출퇴근·휴게는 직원 이름(각 표의 첫 열)이다. 출퇴근은 원래 출근 시각을 눌러 열었다. 하지만 회원 목록 기준에 맞춰 대표 항목인 직원 이름으로 옮겼다.

## 4. 구현 내용

### 상품 관리 > 상품 목록 (`src/features/products/Products.tsx`)

- 카드형 `article` 목록을 `ListTable`(`상품 목록`)로 바꿨다. 열은 상품명(+코드), 유형, 분류, 판매 금액, 이용 조건(+판매 기간·한도), 판매 지점, 상태(+`조회 전용`)다.
- 필터 바에는 검색, 판매 가능 여부, 판매 상태, 상품 유형, 분류, `초기화`, 오른쪽 끝 `상품 등록`을 둔다. 기존 라벨은 `aria-label`로 옮겼다.
  - `판매 가능 여부` 빈 값 문구는 라벨이 사라지므로 `판매 가능 여부 전체`로 바꿨다.
  - `초기화`는 `productSearch`·`productStatus`·`productKind`·`productCategory`·`productAvailability`·`productPage`만 지우고 `tab`은 남긴다.
- 분류 탭에는 판매 가능 여부 필터가 없었다. 작업 지시에는 두 탭에 각각 있다고 되어 있었지만 현재 코드에는 상품 목록 탭에만 있어서, 분류 탭은 손대지 않았다.
- `상품은 삭제할 수 없어요…` 안내는 필터 바 아래(회원 목록 검색 안내 위치)로, 데모 안내는 카드 위로 옮겼다.
- `조회 전용` 행은 긴 설명 대신 짧은 표시와 `title`만 남겼다. 수정 권한 설명은 상세 패널의 안내가 계속 담당한다.

### 공간 관리 > 입퇴실 이력 (`src/features/pass-history/SeatHistory.tsx`, `RangeFilter.tsx`)

- 필터 바에는 이용 지점(전체 범위), 이용 상태, 좌석, 입실 일시 정렬, `초기화`를 둔다.
  - 좌석 select의 안내 문구(`이용 지점을 먼저 선택해 주세요`)는 그대로 뒀다.
  - `초기화`는 필터 키와 page만 지우고 `tab`·`detail`은 남긴다. 단, 이용 지점 필터가 설정돼 있었다면 지점을 바꿀 때와 같은 규칙으로 `detail`도 지운다. 상세 조회가 그 지점 기준이기 때문이다.
- 카드 안 순서는 필터 바 → 기간 조회 행(`inline` `RangeFilter`) → 고객 선택 행 → 좌석 목록 오류(있을 때) → 조회 기준 안내 → 표 → footer다.
- 잘못된 기간 안내는 `ListTable`의 `state`로 표 안에 표시하고 footer는 `항목 수 확인 불가`로 둔다. `상세` 열을 지우고 고객 이름을 셀 링크로 바꿨다. 보조 정보(회원번호, 좌석, 상품, 퇴실, 차감·초과)는 `<br>` 대신 `help` 줄로 바꿨다.
- 기존 표 래퍼의 `role="region"`·`tabIndex` 키보드 스크롤 영역은 다른 공통 목록과 같게 `ListTable`의 `.data-scroll`로 대체됐다.

### 근무 관리 > 출퇴근·휴게 (`src/features/attendance/AttendanceRecords.tsx`)

- 필터 바에는 출근일 시작~종료, 근태 상태, 조회 대상·근태 직원(관리자만), `초기화`를 둔다. `초기화`는 `from`·`to`·`status`·`mine`·`employeeId`·`page`만 지우고 `tab`은 남긴다. 기존 필터 변경 규칙(page·detail 삭제)은 그대로다.
- `DataNotice`와 표 아래 빈 문단 대신 `ListTable`(`출퇴근 기록`)이 로딩·오류·빈 상태를 표 안에 보여 준다. 자체 페이저는 `ListFooter`로 바꿨다.
- 이 때문에 데이터가 이미 있는 상태에서 새로 고침만 실패한 경우의 안내 띠는 없어졌다. 대신 footer가 `항목 수 확인 불가`를 보여 준다. 회원 목록·결제 관리와 같은 처리다.
- 상단 `ClockCard`·`LeaveBalances`(`intro`)와 근무표·기록 정정 등 다른 탭은 바꾸지 않았다.

### 시험

- 신규 `SeatHistory.test.tsx`는 다음을 확인한다.
  - 고객 이름 셀 링크로 상세가 열리고 `detail`이 반영되며 상세 열이 없다.
  - 빈 상태와 잘못된 기간 안내가 표 안에 보인다.
  - 필터를 바꾸면 page가 지워진다.
  - `초기화` 후 `tab`·`detail`만 남는다.
  - 기간 조회 행의 접근성 이름과 적용 동작이 유지된다.
- `Products.test.tsx`는 상세 열기를 표 범위 셀 링크로 바꿨다. `상품 등록`이 필터 바 안에 있는지, `초기화` 범위, 표 안 빈 상태를 확인하는 시험을 추가했다.
- `Attendance.test.tsx`는 상세 열기를 직원 이름 셀 링크로 바꿨다. 표 안 빈 상태, footer, `초기화`를 확인하는 시험을 추가했다.
- Playwright `products`·`usability`·`pass-history`와 live `rooms`·`pass-history` spec은 `상품 상세:`/`이용 상세` 버튼 대신 표 범위의 셀 링크를 찾는다. `attendance.spec.ts`는 행 안의 버튼을 찾는 방식이라 수정 없이 통과했다.

## 5. 검증 결과

- `npx vitest related`로 수정 파일 관련 시험을 실행했다(14파일 171건 통과, 신규 시험 추가 전 기준). 이어서 `npm run typecheck`, `npm run lint`도 통과했다.
- 전체 `npm test`(89파일 795건)와 `npm run build`(live 빌드와 산출물 검사)가 통과했다.
- Playwright MSW는 다른 dev 서버를 재사용하지 않도록 15190 포트 임시 설정(`--strictPort`, `reuseExistingServer: false`)으로 실행했다.
  - 관련 spec(`products`, `usability`, `pass-history`, `attendance`, `customers`, `payments`)은 모두 통과했다. 첫 실행에서 `products.spec.ts`의 직원 시나리오가 `/^상품 상세:/` 정규식으로 버튼을 찾고 있어 실패했다. 표 범위 첫 셀 링크를 찾도록 고친 뒤 통과했다.
  - 전체 MSW 스위트(69건)는 67건 통과, 2건 실패였다. 실패는 `extended.spec.ts:119`(AI clarification)와 `profile.spec.ts:12`(닉네임 저장)로, #106 기록에서 `origin/main`에서도 실패한 것으로 확인한 2건과 같다. 이번 작업에서 새로 생긴 실패는 없다.
- 화면 확인은 MSW dev 서버(15191)에서 했다. 회원 목록과 세 화면(전체·강남점 범위 포함)을 1440/1024/390px로 Playwright Chrome 스크린샷을 찍고 레이아웃을 측정했다.
  - 모든 조합에서 페이지 가로 스크롤, 필터 바 요소 겹침, 카드 밖으로 나간 필터 요소가 없었다.
  - 세 화면 모두 카드 → 필터 바 → 표 → footer 순서이고, 카드 시작 위치가 회원 목록과 같았다.
  - 상품 목록의 `상품 등록`은 회원 목록의 `회원 등록`과 같은 필터 바 오른쪽 끝에 있다.
  - 390px에서 입퇴실 이력 기간 입력과 출퇴근 출근일 입력은 한 줄씩 전체 폭으로 쌓였다.
- 실제 백엔드가 필요한 `tests/live/rooms.spec.ts`, `tests/live/pass-history.spec.ts`는 셀 링크 기준으로 고쳤지만 실행하지 않았다.
- 상세·수정·정정 요청 흐름을 사람이 직접 클릭해 확인하지는 않았다. 단위 시험과 MSW spec(상품 등록·수정, 입퇴실 상세, 근태 상세)으로 확인했다.
- 이 저장소에는 `graphify-out/graph.json`이 없어 graphify 질의·갱신은 실행하지 않았다.

## 6. 남은 작업 / 보류 사항

- 상품 상세를 URL(`detail`)로 옮기는 작업은 단건 조회 흐름이 필요해 보류했다. 필요하면 별도 이슈로 다룬다.
- 결제 관리 기간 입력(#106)은 390px에서 여전히 폭에 따라 줄바꿈된다. 이번에 정한 `sm` 미만 쌓기 규칙을 적용할지는 별도로 정한다.
- `extended.spec.ts`(AI clarification)와 `profile.spec.ts`(닉네임 저장) MSW 시험 실패는 main에서도 재현되는 기존 문제다.
