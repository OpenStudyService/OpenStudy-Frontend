# 2026-11-03 스터디룸·예약 정본 API 연결 (#23)

## 1. 배경 / 문제

Frontend #23의 스터디룸과 예약은 기존 ResourcePage 데모 모델·범용 명령을 사용했다. 루트 AGENTS.md, graphify, 관련 Issue·PR·현재 구현·개발 기록을 확인했다. 최신 Frontend main `9883200`에서 `feature/room-reservation-api`를 만들었다. 기존 미추적 `.gitattributes`와 Backend의 `poc.env` 등 다른 작업은 변경하거나 포함하지 않는다.

Backend #67 계약, #69·#70의 실제 코드와 병합 이력을 확인했다. 룸·예약 PR #151(`0c024e7`), 취소·이용 PR #152(`795d2f6`)은 main에 포함돼 있다. 별도 복사본의 검증 기준은 Backend main `7fcac51`이다.

사용자 요청에 따라 서브에이전트에 계약·API/타입/모델, UI·컴포넌트 검증, Mock 정본 어댑터·MSW 검증을 분담했다. 주 에이전트는 작업 범위 조율·통합·실제 서버/Chrome 검증·개발 기록·PR·CI를 맡았다.

## 2. 검토한 선택지

- 기존 데모 폼을 필드 변환으로 유지하는 방법과 공통 UI를 재사용하면서 정본 모델을 분리하는 방법을 검토했다. 예약의 서버 요금 snapshot·권한별 nullable billing, 별도 이용 기록과 취소 후 신규 예약을 표현하기 위해 정본 전용 화면·폼을 선택했다.
- 별도 견적 API가 없다는 것을 실제 계약·구현에서 확인했다. 가짜 quote 경로 또는 클라이언트 계산 금액 대신 예약 전 서버 시간당 요금, 등록 후 서버 확정 결제 금액을 표시한다.
- 예약 수정 API도 없다. 취소·전액 환불 후 새 요청 키로 새 예약·새 결제를 생성한다. 원래 예약을 덮어쓰지 않는다.

## 3. 결정 및 이유

- 기존 공간 탭·예약 진입점과 Panel, Field, 고객 검색 등 공통 UI를 재사용한다. Panel의 동기 `onOpenAutoFocus`는 유지한다.
- 정본 OpenAPI로 `foundation.generated.ts`를 갱신했다. 기존 타입에는 M6 룸·예약 계약이 없었다. 재생성에 따른 설명·operation 응답 정렬 변경도 정본 출력에 포함된다.
- 생성 타입에 추가된 결제의 룸·사물함 참조는 기존 결제 fixture에서 null로 보완했다. 신규 `customers:cross-branch-read`는 Backend V4의 명시 정책에 따라 기본 관리자 프리셋이나 초기 직원에게 자동 부여하지 않는다. 개별 직원·커스텀 프리셋의 명시적 부여만 허용한다.
- 예약 고객은 기존 판매 가능 고객 검색 범위에서 선택한다. 입실용 정확 일치 조회로 찾은 타 지점 고객은 예약 대상 허용 근거가 아니므로 사용하지 않는다.
- 생성·취소에만 멱등 키를 보내고 동일 입력 재시도는 같은 키를 유지한다. 룸 수정·상태 변경과 이용 시작·완료는 조회 버전을 보낸다.
- 시간은 한국 시간의 날짜·정시 선택과 1~24시간 길이로 제한한다. 취소 버튼은 서버 `canCancel`, 현재 상태·권한, 서버 기준으로 진행하는 시계가 시작 시각 전인지 함께 확인한다.
- 서버 응답의 billing이 null이면 과거 캐시나 데모 값으로 금액·결제 ID를 채우지 않는다. live 실패는 오류로 표시한다.

## 4. 구현 내용

- 룸 목록·상세·등록·변경·운영 중단/재개, 번호·정원·시간당 요금·운영 상태를 연결했다.
- 기간·룸별 예약 목록·달력·상세, 고객 선택·시간 선택·Mock 결제, 취소·전액 환불·새 예약·이용 시작·완료를 연결했다.
- 422 입력 오류, `ROOM_TIME_CONFLICT` 일정 충돌, `VERSION_CONFLICT` 최신값 비교를 구분한다. 충돌에서도 입력을 유지하고 실제 일정을 다시 조회한다. 버전 충돌 재저장은 변경한 필드만 보낸다.
- 제출 동기 잠금·요청 취소·권한 문맥 분리·403 세션 갱신, 성공 상세 캐시의 버전 즉시 반영으로 중복 명령과 늦은 응답 경합을 처리한다.
- 서브에이전트 리뷰에서 룸 상태 변경의 원래 의도가 백그라운드 갱신으로 반대로 바뀌는 경합, 접근 오류 후 과거 룸 제목 노출, 최신 상태 비교 후 부적절한 명령 재실행을 발견해 보완했다.
- MSW는 기존 룸·예약 원장의 정본 메타데이터를 사용한다. 결제 실패 예약은 목록에 남고 달력·슬롯에서는 제외되며, 직원 응답의 billing 숨김이 원장의 결제 정보를 지우지 않는다.

## 5. 검증 결과

검증 실행 결과와 인수 조건별 근거는 최종 통합 검사 후 아래에 누적한다. 실제 HTTP·Chrome은 별도 Backend 복사본과 일회용 MySQL을 사용하며 MSW와 구분한다. 상세 명령·환경·범위는 [실제 서버 검증 문서](../testing/rooms-live.md)에 남겼다.

초기 실제 서버 시험은 시간 충돌 오류 코드에 대한 테스트의 잘못된 기대값을 `ROOM_TIME_CONFLICT`로 바로잡았다. 룸 목록의 표시명이 번호와 이름을 함께 포함해 선택자를 보완했다. 이 결과를 최종 통과로 간주하지 않고 재실행한다.

## 6. 남은 작업 / 보류 사항

- 운영 배포·실제 모바일 기기·부하·다중 인스턴스, Backend 자체 통합 테스트 재실행은 수행하지 않는다.
- 사물함(#24), 타 지점 고객 요약(#25), 채팅 독립 읽음은 이번 범위가 아니다.
- 작업 브랜치만 push하고 main 대상 PR의 CI까지 확인한다. main 직접 push·PR 병합·자동 병합은 하지 않고 사용자 병합을 기다린다.

## 추가 발견과 범위

일반 결제 상세는 기존 이용권 중심의 구매 상품·환불 조건 안내를 사용한다. 룸 예약 화면의 확정 금액·전액 환불·원결제 보존은 이번에 검증했으나, 범용 결제 목록·상세의 룸/사물함 목적별 안내는 별도 후속 개선으로 남긴다. 예약의 권한·결제·환불 동작을 범용 이용권 환불로 우회하지 않는다.

이번 이슈의 필수 인수 조건은 위 검증으로 확인했다. 운영 환경 검증과 후속 개선을 이번 구현 완료와 혼동하지 않는다.
