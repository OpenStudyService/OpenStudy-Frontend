# 업무 관리 화면·권한·데모 동작 준비 (#26, 1단계)

## 1. 배경 / 문제

업무 화면은 범용 ResourcePage의 데모 분기였다. SRS v1.7의 FR-TASK-01~06/08, POL-15 및 Backend ADR-M7-001 M7-D01은 지점 직원 누구나 등록하고 등록자·담당자·해당 지점 MANAGER 이상이 변경하도록 정했지만, 기존 화면과 데모는 관리자만 등록하고 담당 직원은 상태·체크리스트만 바꿀 수 있었다. 등록자 정보도 없었다.

Backend #74는 작업 확인 시 열려 있고 collaboration-api.md 및 정본 OpenAPI의 업무 operation이 없었다. 사용자는 화면부터 병행 준비하고 2개 PR로 진행하도록 선택했다. 이 작업은 첫 PR이며 전체 #26의 실제 API 연결 완료를 뜻하지 않는다.

## 2. 검토한 선택지

- 범용 화면의 업무 분기를 계속 늘리기: 변경 범위는 작지만 등록자 권한·입력 초안·충돌 비교·진입 경로별 상세 처리가 다른 도메인과 섞인다.
- 업무 화면과 통신을 별도 기능으로 옮기기: 기존 디자인과 공통 UI를 유지하면서 이후 계약 연결 지점을 제한할 수 있다. 기존 호출부를 유지하는 분기 래퍼를 두어 업무 목록과 채팅의 상세 진입을 함께 전환한다.

## 3. 결정 및 이유

두 번째 방법을 선택했다. src/features/tasks에 화면·폼·패널·내부 모델·통신 어댑터를 둔다. 기존 ResourcePage와 RecordPanel의 업무 진입만 새 기능으로 위임하고 다른 도메인 동작은 유지한다. Router·Chat의 기존 URL과 호출부를 그대로 사용하므로 채팅 카드도 같은 업무 패널을 연다.

API 어댑터는 이미 쓰던 데모 요청을 사용한다. 새 서버 API나 DTO를 추정하지 않는다. createdById는 선택적인 데모 메타데이터이며 정본 생성 타입을 변경하지 않는다. 등록 시 클라이언트가 등록자를 지정할 수 없고 데모가 로그인 사용자로 기록한다. 이전 데모 데이터에 등록자 값이 없다면 등록자 권한을 추측해 부여하지 않는다.

## 4. 구현 내용

- 제목·지점·담당자·기한·우선순위·상태 목록, 상세·내용·분류·등록자·체크리스트·처리 이력을 업무 전용 화면으로 옮겼다.
- 검색·내 업무·상태·담당자·기한·정렬·방향·페이지는 URL에 유지한다. 목록 요청에서 상세·편집·작업 같은 UI 조건을 제외하고 페이지 이동은 응답의 pageSize를 사용한다.
- 지점 직원 등록과 등록자·담당자·지점 관리자 변경 정책을 화면·데모에 함께 적용한다. 소속 회수는 등록자 권한보다 우선한다. 담당 직원의 제목·내용·담당자·기한 변경도 허용한다.
- 전체 지점 등록은 실제 지점을 선택해야 한다. 담당자 후보는 기존 지점별 lookup의 활성 계정·활성 소속 정보로 확인하고, 지점 변경 시 선택을 해제한다. 최소 id/name 응답으로 소속·활성 상태를 추정하지 않는다. 정본 후보 조회는 #74 이후 연결한다.
- 편집 원본·버전·초안을 분리했다. 재조회가 입력을 덮어쓰지 않는다. 409 뒤 최신 내용을 별도로 보여 주고 사용자 재저장 시 원래 초안에서 바꾼 필드만 최신 버전과 함께 보낸다. 최신 조회가 실패해도 충돌 확인 상태를 유지한다.
- 상태 변경과 체크리스트 충돌은 자동 재실행하지 않는다. 최신 내용을 확인하고 다시 실행해야 한다. 데모에서 잘못된 상태 전이를 거부하고 변경자·시각·전후 내용을 이력에 남긴다.
- 변경 중 이중 제출을 막고 같은 논리 요청 재시도에는 같은 키를 쓴다. 미저장 입력은 닫기·라우터 이동·새로고침 시 확인한다. 로그인·승인 제한 화면으로의 강제 이동은 막지 않는다.
- 계정·지점·권한 문맥이 달라지면 폼을 재생성하고 진행 요청을 중단한다. 읽기 요청에도 AbortSignal을 전달한다. 저장 후 사용자 데이터 캐시를 무효화해 목록·상세·기존 홈·카드가 재조회하도록 한다.
- 기존 데모 공유→카드→상세→완료 흐름을 유지한다. 신규 live 공유는 #27 범위다. live에 데모 fallback이나 가짜 저장 성공을 추가하지 않았다.

## 5. 검증 결과

- 최종 `npm run check`: TypeScript·ESLint 통과, 22개 파일 182개 테스트 통과. 기존 SSE 로컬 HTTP 시험도 포함한다.
- 업무 전용 모델·어댑터·UI 시험은 19개다. 활성 담당자·최소 lookup, 등록자 위조 방지, 역할별 변경과 소속 회수, 부분 PATCH, 422/409 입력 보존, 실패한 최신 조회, 상태·체크리스트의 명시적 재시도, 이중 제출, 요청 중단과 이탈 확인을 검사한다. 별도 기존 domain 시험도 새 정책으로 갱신했다.
- 전체 검사 후 지점 관리자가 등록자·담당자가 아닌 업무를 수정하는 검증과 타 지점 관리자 거절을 기존 모델 시험에 추가했고 해당 5개 모델 시험을 다시 통과했다. 애플리케이션 코드는 추가 변경하지 않았다.
- Chrome `tasks`, `workflows`, `extended`, `smoke`, `responsive`의 17개 모두 통과. 직원 등록·다른 담당자 배정·등록자 수정, 데모 HTTP로 다른 편집자가 변경한 뒤 409 비교·재저장, 취소한 이탈 확인, 직접 편집 URL의 권한 거절, 공유→채팅→체크→완료 및 기존 업무 회귀를 포함한다.
- 1440·1024·390px에서 주요 화면, 입력 폼과 키보드 포커스 복귀를 검사했다. 모바일 업무 폼과 데스크톱 업무 목록 캡처를 직접 확인했다.
- `npm run test:builds`: live 및 demo 운영 빌드와 모드별 Chrome 2개 통과. live가 MSW·데모 로그인을 활성화하지 않고 실제 API 실패를 표시하며 demo는 번들 MSW로 로그인함을 확인한다.
- 최초 단위 실행에서는 과거 담당자 수정 제한을 기대한 시험 1개와 샌드박스 localhost EACCES에 의한 SSE 시험 3개가 실패했다. 정책 시험을 갱신하고 허용된 로컬 실행으로 최종 검증했다.
- 최초 브라우저 실행은 16개 통과·신규 이탈 확인 1개 실패였다. 첫 확인창 응답 처리를 기다리지 않아 두 이벤트 처리기가 겹친 테스트 문제를 수정했다. 최종 재실행은 17개 모두 통과했다.
- Vite 개발 로그의 HydrateFallback 경고와 MSW 시연 중 일부 /api/me 프록시 연결 거절은 실제 Backend 연결 성공 근거로 사용하지 않는다. 해당 개발 실행에서도 위 브라우저 시나리오와 화면의 스크립트 오류 검사는 통과했다.
- `git diff --check` 통과. `graphify update .` 완료(1,078 nodes, 3,154 edges, 62 communities). AST-only 갱신이며 일부 설정·데이터 파일의 심볼 미추출과 커뮤니티 이름 갱신 안내가 있었다. 원래 무시되는 graphify 산출물은 새로 커밋하지 않는다.
