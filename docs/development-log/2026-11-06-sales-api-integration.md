# 2026-11-06 매출·지점 비교·최소 원장 실제 API 연결 — #30 1차

## 1. 배경 / 문제

Frontend [#30](https://github.com/OpenStudyService/OpenStudy-Frontend/issues/30)의 기존 매출 화면은 데모 `/sales`와 고정된 과거 기간에 의존했다. Backend #86 계약과 #87 구현([PR #162](https://github.com/OpenStudyService/OpenStudy-Backend/pull/162))은 main에 병합됐지만 #88 판매량·상품 순위·추세는 아직 병합되지 않았다. 열린 이슈 상태만 보지 않고 계약, 코드, 병합 이력과 기존 기록을 대조했다.

Frontend main `972fbdb`에서 `feature/sales-api-integration`을 만들었다. 기존 미추적 `.gitattributes`는 변경·포함하지 않는다. Backend 작업 트리에 있는 #88 등의 병행 변경과 환경 파일은 사용하거나 수정하지 않는다. 계약 생성과 실제 서버 검증은 고정 커밋 `90f5ec2`만 사용한다.

작업 재개 후 최종 브랜치 확인에서 워크스페이스가 다른 작업의 병합을 포함한 main `3dfa936`으로 전환되어 있음을 확인했다. 최초 작업 브랜치에는 별도 커밋이 없고 모든 변경이 작업 트리에 유지돼 있었다. 현재 main을 기준으로 `feature/sales-revenue-integration`을 새로 만들어 이번 변경을 그대로 옮겼다. 최종 검사와 커밋·push는 이 브랜치에서 수행하며 main에 커밋하지 않는다. 재개 후 검증은 이미 이 최신 작업 트리의 코드를 사용했다.

## 2. 검토한 선택지

- #88까지 준비될 때 기다리거나, 이미 준비된 매출·지점 비교·원장을 먼저 제공하는 방법을 비교했다. 사용자가 승인한 1차 범위로 실제 연결하고 #30 전체 완료와 구분한다.
- 기존 차트·표를 모두 바꾸지 않고 지점 비교 차트를 재사용한다. 합계·지표·조건을 정본 모델로 바꾸고 원장과 용도별 표를 추가한다.
- 여러 GET의 기준 시각이 같다는 보장은 계약에 없다. 각 영역의 서버 메타정보와 기준 시각을 각각 표시하고 같은 스냅샷처럼 꾸미지 않는다.

## 3. 결정 및 이유

매출은 `/sales/revenue`, `/sales/revenue/branches`, `/sales/ledger`만 사용한다. 지점은 반복 `branchIds`, 기간은 한국 시간 날짜를 UTC로 변환한 시작 이상·종료 미만이다. 기간을 비우면 서버가 이번 달 1일부터 내일 0시까지 정하고, 화면은 실제 적용 기간을 표시한다. 한쪽 날짜·역전·366일 초과는 요청 전에 안내한다.

서버가 반환하는 합계와 메타를 표시한다. 잘못된 응답·빈 HTTP 본문을 0원이나 빈 목록으로 바꾸지 않는다. 0원 거래와 거래 없음, 비율 해당 없음을 구분한다. 지점 선택은 현재 `sales:read` 범위로 제한하고 결제 링크는 서버 `canViewPayment`와 현재 `payments:read`를 함께 확인한다.

생성 OpenAPI의 nullable allOf ID가 string으로 남는 기존 생성기 한계는 생성물을 수동 편집하지 않고 좁은 런타임 DTO에서 보정한다. 생성 타입은 고정 Backend 정본에서 재생성했다.

## 4. 구현 내용

- 매출 카드·용도별 소계·지점 비교 차트/표·최소 원장, 기간·지점·용도·환불 기준과 정렬·페이지를 URL에 연결했다. 거래가 없으면 차트를 만들지 않는다. 지점 차트는 첫 20개와 생략 안내, 표는 전체를 제공한다.
- 합계·건수·지점·기간·기본 기간·메타 단위·원장 부호·참조·전체 페이지 합계를 런타임 검증한다. 개인정보가 추가된 원장도 거절한다.
- 계정·권한·지점 문맥을 조회 키에 포함해 과거 데이터가 새 문맥에 표시되지 않게 한다. 늦은 응답과 권한 회수 회귀를 추가했다.
- 공통 금액·숫자·비율·한국 시각 형식을 만들고 기존 결제·이용권·좌석·룸의 형식 함수에 연결했다. 정상값 표현을 유지하며 null/잘못된 값과 bigint 경계를 검사한다.
- MSW는 기존 결제·환불·룸·사물함 공유 원장에서 집계한다. 별도 고정 매출 합계를 만들지 않는다. 상품 스냅샷은 기존 Mock 메모리 원장을 재사용하며 새로고침 후 스냅샷 복원 한계는 실제 Backend 영속성 검증과 구분한다.
- 사용자의 요청으로 서브에이전트가 API·화면·공통 형식을 분담했고 상호 검토에서 원장 합계·항목 필터·지표 단위·기본 기간 검증을 보강했다.

## 5. 검증 결과

최종 통합 결과와 실행 중 발견한 문제는 아래에 누적한다. 실제 서버 재현 방법은 [sales-live.md](../testing/sales-live.md)에 기록한다.

- 집중 검사: API 17개, MSW 집계 7개, UI 12개 통과. 기존 결제 검사 8개도 확대 실행에서 통과했다.
- 초기 전체 검사에서 상태 요소의 전역 개수를 고정한 신규 테스트가 실패했다. URL 표시용 output도 status 역할이므로 각 매출 영역 안의 상태로 범위를 좁혔다. 관련 12개 재검사 통과. 제품의 계정 전환 데이터 노출은 재현되지 않았다.
- 독립 Backend `90f5ec2`의 JDK 21 `bootJar` 성공. Backend 자체 전체 테스트를 재실행한 것은 아니다.
- live/mock 빌드·오염 검사와 산출물 Chrome 5개 통과. 기존 500KB chunk 권고는 남는다. 이 검사는 HTTP fixture이며 실제 Backend 검사와 구분한다.
- 기존 의존성에 접근성 패키지가 누락돼 타입 검사가 실패했다. npm ci는 기존 실행 프로세스가 잡고 있는 native 모듈 때문에 EPERM이어서 중단됐고, 원래 서버를 종료하지 않고 의존성을 복원했다. package-lock은 변경하지 않았다.
- 최종 전체 `npm run check` 통과: typecheck·ESLint, Vitest 74파일/612개, 메일 도구 자체 검사 9개, 빌드 가드 19개. 메일 자체 검사는 실제 발송 시험이 아니다.
- Mock Chrome의 신규 검사에서 전체 합계 400,000원 대신 한 지점 금액 300,000원을 기대한 단언을 바로잡았다. 실제 화면 수치는 공유 원장과 일치했다. 기존 결제·예약 workflow의 구형 예약 필드 선택자도 현재 정본 예약 날짜·정시·이용 시간 선택으로 맞췄다.
- 신규 매출 화면 axe 검사에서 가로 스크롤 표에 키보드 진입점이 없는 문제(`scrollable-region-focusable`)를 발견해 표 래퍼에 `tabIndex=0`을 적용했다. 검사 기준을 완화하지 않았다.
- 실제 Backend·일회용 MySQL·Chrome 3개가 운영 빌드에서 통과했다(9.4초). 실제 고객·상품·결제·환불 API로 만든 원장의 세 조회 합계·새로고침·조건 복원, 매출 전용 직원의 지점·결제 링크 제한, 무권한 직원 403, 빈 기간과 366일 사전 차단을 확인했다. 로그인 UI 검증은 포함하지 않는다.
- 초기 실제 시험에서 홈/SSE를 열어 둔 채 거래를 준비하면 재조회가 반복됐고, 같은 작업 폴더의 live/mock 개발 서버 병행 시 최초 진입·로그인 대기가 불안정했다. DB 프로세스는 Sleep으로 쿼리 잠금 대기가 없었다. 검증용 Backend를 파일 로그 방식으로 재시작하고 API로 준비한 뒤 운영 preview로 직접 진입하도록 바꿨다. 어떤 한 원인으로 단정하거나 제품 오류를 대체 응답으로 숨기지 않았다. URL 체크박스·select의 비동기 반영과 정확한 접근성 이름을 기다리는 단언도 보완했다.
- Mock 운영 빌드 Chrome 최종 10개 전체 통과(48.6초): 신규 매출 세 테마·1440/1024/390px·axe serious/critical, 기존 전체 화면·반응형·업무 공유·결제/환불/예약 충돌·AI 데모 수치 비교·직원 권한을 확인했다.
- 실제 desktop/mobile 캡처를 확인하고 좁은 화면에서 금액과 원 단위가 분리되는 카드 배치를 한 열로 보완했다. 앱 내부 스크롤 때문에 전체 페이지 캡처에 공백이 생길 수 있어 원장까지 스크롤한 viewport 캡처도 확인한다.
- 모바일 보완 이후 최종 `npm run check`도 동일한 74파일/612개와 도구 검사 9개·빌드 가드 19개로 통과했다. 최종 live/mock 운영 빌드와 오염 검사, 실제 서버 Chrome 3개(19.9초), Mock Chrome 10개(57.7초), 산출물 Chrome 5개(9.7초)가 모두 통과했다. 실제 모바일 원장 캡처에서 금액·원 단위가 같은 줄로 표시됨을 확인했다.
- 최종 Frontend `graphify update .`: 2,751 nodes / 8,252 edges / 125 communities. AST만 사용했으며 API 비용은 없다. 기존 `tree_sitter_sql` 미설치로 SQL 3개가 그래프에서 빠진 경고는 남고 기능 테스트 결과와 별개다. 그래프는 기존 ignore 정책에 따라 로컬에 유지한다.
- 검증용 Backend PID `4268`의 jar 절대 경로와 MySQL 컨테이너 전체 ID `ae1d65521a06e958a3f6ca3f27491a8c2b2afe03cc4bd1a3f93a85cfdc627fd3`·이름을 대조한 뒤 종료·제거했다. 경로를 확인한 이번 QA 사본·임시 자격 증명과 익명 볼륨도 정리했다. 사용자 DB·원래 서버·Backend 작업 트리는 정리하지 않았다.
- 자동 승인 검토 사용량 한도로 브라우저 재검사 한 번이 실행되지 않았다. 사용자의 재개 요청 후 같은 승인 경로로 정상 실행했고 제한을 우회하지 않았다. 사용자의 추가 지시에 따라 이후 작업은 서브에이전트 없이 주 세션에서 수행했다.

## 6. 남은 작업 / 보류 사항

- 마지막 상태 확인에서 Backend #88이 [PR #165](https://github.com/OpenStudyService/OpenStudy-Backend/pull/165)(`1bbf252`)로 병합되고 이슈가 종료된 것을 확인했다. 착수 당시에는 미병합이어서 합의한 1차 범위에는 포함하지 않았다. 이후 이용권 판매량·발급 건수·상품 순위·일/주/월 추세를 연결하는 2차 작업은 바로 착수할 수 있다. 이번 PR은 #30을 자동 종료하지 않는다.
- 운영 배포·운영 DB·실제 모바일 기기·다중 인스턴스·대용량 성능·Backend 전체 테스트 재실행은 수행하지 않는다.
- 작업 브랜치 push와 PR 준비까지만 수행하고 main 반영·PR 병합·자동 병합은 사용자에게 맡긴다.
