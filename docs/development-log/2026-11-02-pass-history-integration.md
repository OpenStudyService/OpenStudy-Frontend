# 2026-11-02 입퇴실 이력·이용권 조정·고객 내역 API 연결 (#22)

## 1. 배경 / 문제

고객·결제·좌석 입퇴실은 실제 API에 연결됐지만 이력과 수동 조정은 남아 있었다. Issue #22, 병합된 Frontend PR #50·#52·#55, Backend #60·#64와 PR #142·#143, 기존 개발 기록을 대조했다. 최신 main `242af5b`에서 `feature/pass-history-integration`을 만들었다. 기존 미추적 `.gitattributes`는 변경하거나 포함하지 않는다.

## 2. 검토한 선택지

입퇴실 이력을 범용 리소스 화면에 계속 넣는 방법과 정본 DTO 전용 화면을 연결하는 방법을 검토했다. 중첩된 구매·이용 지점과 서버 정산량이 기존 데모 필드와 달라 전용 화면을 사용하고, 기존 패널·표·고객 선택기·페이지·오류·이탈 방지 기능을 재사용했다.

## 3. 결정 및 이유

- 한국 시각 입력을 명시적으로 UTC로 변환한다. 조회는 `[from,to)`이며 입퇴실은 입실 시각, 고객 내역은 사건 시각 기준이다. 원장 대조는 기간과 무관한 전체 합계다.
- 조정은 증감량이 아닌 조정 후 값이다. 초기 편집 버전을 유지하고, 사용자가 변경한 필드만 보낸다. 충돌 후 명시적으로 읽은 최신 버전을 적용하므로 동시 변경된 다른 필드를 덮어쓰지 않는다.
- 구매 지점의 `payments:write`로 버튼을 제한하고 환불 이용권은 조정하지 않는다. 서버가 다시 판정한다. 응답 유실은 입력을 잠그고 최초 본문·키로 재시도한다. 중복 제출과 화면 이탈 후 늦은 성공 응답을 막는다.
- 고객 내역은 허용 범위 내 구매 이용권만 표시한다. 타 지점 이용은 지점·시각·증감량으로 제한하고 처리자·사유·이용 분·기록 ID를 표시하지 않는다. 결제 링크에는 별도 결제 조회 권한을 확인한다.
- 기존 생성 타입에는 조정 anyOf가 `unknown`으로, 내역의 nullable 참조가 string으로 생성된다. 생성 파일을 수동 편집하지 않고 문서화된 요청형과 두 참조의 nullable 보정형을 좁은 어댑터에 정의했다. 런타임 검증으로 잘못된 응답·고객·구매 지점·기간을 차단한다.

## 4. 구현 내용

- 입퇴실 이력 목록·이용 지점·좌석·고객·상태·기간·정렬·페이지와 이동 이력 상세를 연결했다. 종료된 이용에 현재 이용권 잔량을 표시하지 않는다.
- 이용권 상세에 유형별 잔량·만료 조정, 사유, 충돌 비교와 재시도를 추가했다. 고객 상세에 구매·사용·환불·조정 내역과 전체 원장 대조를 연결했다.
- MSW는 기존 결제·이용권·좌석 원장을 공유한다. 새 사유·처리자와 조정 멱등 결과는 메모리에만 둔다. 이전 합성 fixture/새로고침의 잔량 스냅샷은 명시적인 초기 데모 잔량 이관 사건으로 표시한다.
- 모바일 표는 기존 data-table·data-scroll을 사용해 가로 스크롤과 키보드 접근을 지원한다.

## 5. 검증 결과

- `npm run check`: typecheck·lint, Vitest 47개 파일 405개, 메일 도구 9개, 빌드 가드 19개 통과. 최초 일반 sandbox 실행의 기존 SSE 소켓 검사 3개는 EACCES였으며 소켓 접근 가능한 환경에서 전체 재검사해 통과했다.
- live/mock 운영 빌드·오염 검사 및 Chrome 산출물 검사 5개 통과. 기존 500KB chunk 경고는 남는다.
- 실제 Backend `adcf15c`를 독립 추출·빌드하고 일회용 MySQL 8.4와 Chrome으로 위 재현 문서의 4개 시나리오를 모두 통과했다(40.3초). 실제 저장·새로고침, 세 역할의 권한, 두 세션 충돌, 실제 커밋 후 응답 유실, 원장 합계, 기간 경계와 세 이용권 유형을 확인했다. Backend 자체 통합 테스트는 재실행하지 않았다.
- MSW 신규 Chrome 3개 통과. 초기 테스트의 전체 페이지 이동은 메모리 사유를 초기화하므로 앱 내 탭 이동으로 수정했다. Chrome 날짜 입력은 분 단위 형식으로 수정했다. 초기 테스트 fixture의 직원 ID·사용 기록 상태와 일회용 DB 운영시간 열 이름을 실제 정의에 맞게 보완했다.
- 회원·결제·좌석·업무·반응형·smoke Chrome 회귀 22개 중 21개가 통과했고, 기존 결제 시험 한 개가 이전 좌석 상태/assign API를 사용함을 발견했다. 정본 `사용 가능`·`POST /seat-sessions`로 수정하고 재검증한다.
- 모바일 고객 내역·조정 캡처를 직접 검토하고 표 간격·가로 스크롤을 보완했다.

## 6. 남은 작업 / 보류 사항

운영 배포·부하·다중 인스턴스·실제 모바일 기기 검증은 수행하지 않았다. 내역 API는 페이지가 없으므로 대량 사건 응답 크기는 Backend 후속 검토 대상이다. 타 지점 최소 요약(#25)과 분석(M9)은 포함하지 않는다.

PR은 작업 브랜치로만 준비하고 main 직접 push·병합·자동 병합은 수행하지 않는다. 실제 서버 검증 환경은 PID·jar 경로·컨테이너 ID를 확인해 정리한다.

## 최종 검증 및 정리

- 기존 결제 회귀 시험을 정본 좌석 계약으로 수정한 뒤 별도 Mock 포트에서 재검증했다. 첫 재시도는 5173의 기존 live 서버를 재사용해 데모 로그인 버튼이 없었으므로 15184 전용 Mock 서버로 분리했다.
- `graphify update .` 완료: 1,853 nodes / 5,552 edges. 출력은 기존 저장소 규칙대로 로컬에서 관리한다. `git diff --check` 통과.
- PID 명령줄의 검증용 jar 경로와 컨테이너 ID·이름을 대조한 후 해당 서버·DB만 종료·제거했고 임시 자격 증명 파일도 삭제했다.
- 보완한 결제 모바일 회귀 검사 1개 통과(24.9초). 앞선 21개 성공과 합쳐 선택한 Chrome 회귀 22개를 모두 확인했다. 동일 시점 한 번의 전체 22개 재실행을 뜻하지 않는다.
