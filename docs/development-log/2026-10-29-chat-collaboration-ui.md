# 2026-10-29 — Frontend #27 채팅·채널 관리·업무 공유 화면 준비

## 1. 배경 / 문제

- [Frontend #27](https://github.com/OpenStudyService/OpenStudy-Frontend/issues/27)의 채널 관리, 메시지·스레드, 읽음, 업무 카드 흐름을 준비한다. 업무 상세는 main에 병합된 [#37](https://github.com/OpenStudyService/OpenStudy-Frontend/pull/37)의 패널과 처리 이력을 재사용한다.
- SRS v1.11의 FR-CHAT-01/02/04~07/09, FR-TASK-07 및 ADR-M7-001을 기준으로 한다. 기존 화면은 메시지 재전송과 커서 조회를 제공하지만, 관리 권한과 참여 권한의 분리, 화면 이동 후 전송 대기 보존, 스레드별 읽음 및 업무 공유 조건을 보완할 필요가 있었다.
- 사용자가 승인한 2단계 계획 중 첫 번째 PR이다. 실제 API 연결은 사용자 병합 후 별도 브랜치에서 진행하며, 이번 변경으로 #27을 완료 처리하지 않는다. `main`의 `724d6c1`에서 `feature/chat-collaboration-ui`를 생성했다.

## 2. 검토한 선택지

- 기존 채팅 화면·스타일·데모 전송 경로를 유지하면서 기능별 컴포넌트와 어댑터로 분리하는 방식을 선택했다. Backend #74의 미확정 DTO나 읽음 계약을 화면에 미리 고정하는 방식은 사용하지 않았다.
- 사용자는 채팅 전용 SSE 도입 대신 보이는 화면에서 15초마다 재조회하는 방식을 선택했다. 기존 공통 workspace SSE는 권한 회수·세션 종료·재연결 및 캐시 갱신에 계속 사용한다.
- 사용자는 채널 본문과 각 스레드의 읽음을 분리하고, 열지 않은 스레드 답글을 채널 본문의 읽음에 포함하지 않도록 선택했다. 기존 채널 단위 최댓값 하나로는 이 동작을 표현할 수 없다.

## 3. 결정 및 이유

- 관리용 채널 목록과 참여 중인 대화 목록을 분리했다. 관리자는 참여하지 않은 채널의 이름·설명·참여자를 편집할 수 있지만 메시지는 조회할 수 없다. 선택한 참여자만 저장하며 관리자를 자동 추가하지 않는다.
- 계정 활성 상태와 현재 지점 접근을 데모에서도 확인한다. 소속 회수로 제거한 참여자는 소속이 복원되어도 자동으로 재참여시키지 않는다. 전체 지점 선택이 다른 지점의 관리 권한을 확대하지 않는다.
- 초안과 전송 대기는 사용자·지점·채널·스레드별 메모리에 둔다. 일반 화면 이동으로 유지하고, 계정·지점 변경 및 권한 회수 시 기존 요청을 중단하고 정리한다. 브라우저 저장소에는 추가하지 않는다.
- 재전송 시 원래 본문과 메시지 키를 유지한다. 같은 대화의 진행 중 전송은 동기적으로 잠그고, 응답 유실 후 조회로 확인된 전송도 대기 목록에서 정리한다. 이전 성공 응답은 다른 내용의 새 초안을 지우지 않는다.
- 과거 기록과 새 기록은 ID로 병합하고 순서를 유지한다. 새 메시지가 한 페이지를 넘으면 기존 최신 메시지까지 커서를 따라 보충한다. 커서 반복·조회 오류가 있으면 성공으로 처리하거나 읽음 위치를 전진시키지 않는다.
- 읽음은 문서와 대화 영역이 실제 보이며 하단 메시지가 표시될 때만 저장한다. 실패를 성공으로 기억하지 않고 다시 시도할 수 있게 했다. 본문과 스레드의 위치는 별도다. 읽음 이벤트는 채널 배지만 갱신하여 불필요한 메시지 재조회와 읽음 요청 순환을 막는다.
- 업무 공유는 업무 조회 권한과 채널 참여를 조건으로 한다. 수정 권한은 요구하지 않는다. 공유 채널은 사용자가 직접 선택한다. 카드 내용은 업무 원본을 재조회하고, 자동 공유 문구는 제목을 포함하지 않아 접근 불가 사용자에게 과거 제목을 노출하지 않는다.

## 4. 구현 내용

- `src/features/chat/`에 관리 화면, 업무 공유·카드, 대화 뷰포트, 조회 훅, 통신 어댑터, 메모리 세션 및 정책·병합 모델을 분리했다. 기존 Enter 전송, Shift+Enter 줄바꿈과 한글 조합 처리를 유지한다.
- 설정의 `tab=channels` 진입을 유지하고 전용 관리 컴포넌트로 연결했다. 활성 직원 후보 조회, 지점 변경 시 참여자 초기화, 중복 제출 방지, 미저장 이탈 확인과 409 입력 보존·최신값 비교를 제공한다. 충돌 후에는 사용자가 변경한 필드만 최신 버전으로 다시 저장한다.
- 15초 갱신·수동 갱신·화면 복귀 갱신을 제공한다. 숨김 상태에서는 주기 요청을 보내지 않고 채팅 이탈 시 타이머를 정리한다. 중복 갱신을 막고 과거 기록·스크롤 기준점·입력을 보존한다.
- 데모 참여 검사와 읽음·읽지 않은 수 계산을 보완했다. 실패 시나리오 전환은 권한 변경 이벤트로 보내지 않도록 수정했다. 이 구분이 없으면 단순 네트워크 실패 시험도 개인 초안과 전송 대기를 지웠다.
- task 카드의 403/404는 `접근 불가`, 서버·네트워크 오류는 별도 재조회 상태로 표시한다. 카드에서 여는 상세는 기존 업무 패널과 이력을 사용한다. 카드 직접 수정 기능은 추가하지 않았다.
- 기존 데모 DM과 공통 workspace SSE를 유지한다. live 빌드에는 데모 대체나 저장 성공 처리를 추가하지 않았다. 미확정 스레드 읽음 요청을 실제 서버에 보내지 않고 연결 준비 상태를 명시한다.

## 6. 남은 작업 / 계약 인계

- 첫 PR의 사용자 병합 후 `main`에서 `feature/chat-api-integration`을 만들고 Backend #74 계약을 확인한다. 참여 채널과 관리 채널, 후보의 지점·활성 보장, 버전 충돌, 메시지 키·커서·보충 및 업무 접근 거절 계약이 필요하다.
- **본문과 스레드별 읽음 대상·위치·읽지 않은 수 계산은 이번 대화에서 사용자가 선택한 정책이다.** 현재 데모의 `parentId`와 별도 read key는 화면 시험용 표현이다. 단일 채널 읽음 위치만 제공하는 서버 계약을 이 정책의 구현 완료로 간주하지 않는다. Backend #74에서 독립된 읽음 계약을 확인하고 `api:foundation`으로 정본 타입을 생성한다.
- Backend #75·#76·#77 및 선행 계약이 준비되면 실제 서버·별도 DB·두 사용자 세션으로 저장 지속성, 응답 유실 후 중복 방지, 참여 종료 직후 거절, 스레드별 읽음 등을 검증한다. 준비되지 않은 항목은 #27의 남은 작업으로 유지한다.
- 신규 DM 연동과 채팅 전용 SSE는 M14 범위다. 채팅 API의 재시도·멱등 정책은 확정 계약을 따른다.
- 작업 전 존재하던 `.gitattributes`는 이번 변경에 포함하지 않는다. 원격 `main` 반영과 PR 병합은 사용자가 수행한다.
