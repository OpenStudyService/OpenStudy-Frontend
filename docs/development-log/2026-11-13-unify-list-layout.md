# 2026-11-13 · 목록 화면 공통 레이아웃 정리 및 보유 이용권·결제 화면 적용

관련 이슈: [#106](https://github.com/OpenStudyService/OpenStudy-Frontend/issues/106)

## 1. 배경 / 문제

회원 관리 메뉴의 회원 목록과 보유 이용권 탭, 결제 관리 화면이 서로 다른 형태였다.

- 회원 목록: 카드 하나 안에 필터 바(검색·라벨 없는 select·초기화·오른쪽 끝 주요 버튼) → 표(로딩·오류·빈 상태도 표 안) → footer(`총 N건 · N페이지`, 이전/다음). 상세는 이름 셀 링크로 연다.
- 보유 이용권·결제 관리: 카드 없이 `Field` 라벨이 달린 select 4열 그리드, 표 밖의 빈 상태·로딩, `SalesPager`, 마지막 열의 `상세: {id}` 버튼.

의도한 차이가 아니라 #19, #20에서 따로 만들어진 결과였다([2026-11-01 기록](2026-11-01-payment-pass-refund-api.md)). 업무·좌석·사물함·매출 등 대부분의 목록도 이미 필터 바 + 카드 형태라서 회원 목록 형태를 기준으로 삼았다.

## 2. 검토한 선택지

- **각 화면의 마크업·CSS만 회원 목록과 비슷하게 맞추기**: 변경이 작지만 같은 마크업이 세 벌 남고, #109(상품·입퇴실 이력·출퇴근·휴게)에서 또 따로 맞춰야 한다.
- **회원 목록 구조를 얇은 공용 컴포넌트로 뽑기**: 배치·상태 표시·footer 규칙을 한 곳에서 관리한다. 필터 값·URL 처리·행 렌더링까지 추상화하면 화면마다 다른 URL 규칙(`useSalesSearch`, 회원 목록의 `setParams`)을 억지로 맞춰야 하므로 범위를 배치에 한정했다.

## 3. 결정 및 이유

공용 컴포넌트를 만들되 **배치와 상태 표시만** 담당하게 했다. 필터 값, URL 파라미터, 행 내용은 각 화면이 그대로 소유한다. 그래서 필터·정렬·페이지·상세의 URL 규칙과 환불·Mock 결제·권한 동작을 바꾸지 않고 형태만 통일할 수 있었다.

- 상세 열기는 회원 목록처럼 **고객 이름 셀 링크**로 통일했다(두 화면 모두 첫 열). 이슈 문구와 회원 목록 위치를 따랐다. 고객 이름을 눌러도 고객이 아니라 그 행의 이용권/결제 상세가 열린다는 점은 감수했다.
- `SalesPager`는 `SeatHistory`도 쓰므로 동작을 바꾸지 않고, 두 화면에서만 공용 footer로 교체했다.
- `Mock 결제` 버튼은 회원 등록처럼 필터 바 오른쪽 끝으로 옮겼다. 결제 조회 권한이 없어 필터 바가 보이지 않는 쓰기 전용 사용자를 위해 그 경우에는 기존처럼 제목 옆에 둔다.

## 4. 구현 내용

### 공용 레이아웃 `src/shared/ui/ListLayout.tsx`

| 컴포넌트 | 역할 |
|---|---|
| `ListCard` | `card overflow-hidden` 래퍼 |
| `ListFilters` | `.filters` 바. `actions`는 오른쪽 끝(`ml-auto`)에 둔다. |
| `ListTable` | `label`(표 접근성 이름), `columns`(헤더 문자열 배열), `state` > `loading` > `error`(+`onRetry`) > `isEmpty`/`empty` 순으로 하나를 표 안 `colSpan` 셀에 보여 주고, 없으면 `children` 행을 그린다. |
| `ListFooter` | `총 N건 · N페이지`, 로딩 중 `항목 수 확인 중`, 오류 시 `항목 수 확인 불가`. 이전은 1페이지·로딩·오류에서, 다음은 마지막 페이지·로딩·오류에서 비활성. |

### 화면 적용

- **회원 목록**: 마크업만 공용 컴포넌트로 바꿨다. 문구·aria-label·동작은 같고 기존 시험을 수정하지 않고 통과했다.
- **보유 이용권**: 상태·유형·지점(전체 범위)·정렬·방향 select를 필터 바로 옮겼다(기존 라벨은 `aria-label`로 유지). `초기화`를 추가했다(필터 키와 page만 지우고 `tab`·`detail`은 유지). `CustomerSelector`는 필터 바 아래 카드 안 보조 행에 두고, `MockPaymentNotice`는 회원 목록의 데모 안내 위치(카드 위)에 둔다.
- **결제 관리**: 상태·지점·기간(시작~종료)·정렬·방향 + `초기화`(고급 필터 포함) + 오른쪽 끝 `Mock 결제` 순서다. 카드 안에 고급 필터(`<details>`), 고객 선택 행, 적용 조건·합계 요약 띠, 표, footer를 둔다. 잘못된 기간 안내도 표 안에 표시하고 footer는 `항목 수 확인 불가`로 둔다.
- `useSalesSearch`에 지정한 키만 지우는 `reset`을 추가했다(기존 `update` 동작은 같음). `CustomerSelector`와 `AdvancedFilters`에는 배치용 `className`만 추가했다(기본값이 기존 클래스라 결제 등록·매출 화면은 그대로다).

### #109에서 재사용하는 방법

1. 화면 루트에서 `<ListCard>`로 감싼다.
2. 라벨 달린 필터 그리드를 `<ListFilters actions={주요 버튼}>` 안의 라벨 없는 select/input으로 바꾼다. 기존 라벨 문자열은 `aria-label`로 옮겨 시험·접근성 이름을 유지한다. 초기화 버튼을 둔다.
3. 표와 표 밖 `State`/`ErrorState`를 `<ListTable label columns loading error onRetry isEmpty empty>`로 합친다. 조건 오류처럼 조회 전에 막는 안내는 `state`로 넘긴다.
4. `Pager`/`SalesPager`를 `<ListFooter>`로 바꾼다. 다른 화면이 같은 페이저를 쓰면 그 컴포넌트 자체는 수정하지 않는다.
5. `상세: {name}` 버튼을 대표 항목 셀의 `<button className="cell-link">`로 바꾸고, 그 버튼을 role/name으로 찾던 시험은 표 범위(`getByRole("table", { name })`) 안에서 찾도록 고친다. 다른 표에도 같은 이름의 셀 링크가 생길 수 있어서다.

## 5. 검증 결과

- 공용 레이아웃 시험 `ListLayout.test.tsx`를 추가했다. 표 안 빈/로딩/오류 상태와 `colSpan`, `state` 우선순위, actions 위치, footer 건수 문구, 이전/다음 비활성을 확인한다.
- `Payments.test.tsx`에 시험을 추가했다. 두 화면에서 고객 이름 셀 링크로 상세 패널이 열리고 `detail`이 URL에 반영되며 상세 버튼·상세 열이 없는지, 필터 변경 시 page가 지워지는지, 초기화가 필터 키만 지우는지, 잘못된 기간 안내·빈 상태가 표 안에 있는지, `Mock 결제`가 필터 바 안에 있는지 확인한다.
- `npx vitest related`(13파일 152건), `npm run typecheck`, `npm run lint` 통과.
- 전체 `npm test`(88파일 779건) 통과, `npm run build`(live 빌드와 산출물 검사) 통과.
- Playwright MSW: 다른 작업의 dev 서버(5173)를 재사용하지 않도록 15190 포트 임시 설정으로 실행했다.
  - `payments`·`workflows`·`pass-history`·`customers` spec 통과.
  - `pass-history`의 회원 이름 버튼 조회는 보유 이용권 표에도 같은 이름의 셀 링크가 생겨 모호해졌다. 그래서 회원 목록 표 범위로 좁혔다.
  - 전체 MSW 스위트(69건)는 63건 통과, 6건 실패였다. 실패한 6건(근태 2, 채팅 1, AI 분석 1, 초대 1, 프로필 1)을 부하 없이 다시 실행해 깨끗한 `origin/main` worktree와 비교했다. 두 쪽 모두 `extended.spec.ts`의 AI clarification과 `profile.spec.ts`의 닉네임 저장 2건만 실패하고 나머지 6건은 통과했다. 이 2건은 main에서도 실패하므로 이번 변경과 무관하다. 근태·채팅·초대 실패는 전체 실행 중 Vitest·빌드를 동시에 돌린 부하에 따른 시간 초과로 본다.
- 화면 확인(MSW dev 서버, Playwright Chrome으로 1440/1024/390px 스크린샷과 레이아웃 측정)
  - 회원 목록 ↔ 보유 이용권 탭 전환 시 카드·필터 바·표·footer 위치가 같았다.
  - 세 폭에서 페이지 가로 스크롤, 필터 바 요소 겹침, 카드 밖으로 나간 요소가 없었다.
  - 보유 이용권 고객 이름 클릭으로 상세 패널이 열렸다.
  - 1024px 전체 범위 결제 화면은 `Mock 결제` 버튼이, 390px은 기간 종료 입력이 다음 줄로 넘어간다(겹침 없음).
  - 데스크톱 앱 브라우저 창에서는 로컬 서버를 열 수 없어 Playwright 스크린샷으로 대신했다.
- 결제 상세·환불·Mock 결제 흐름은 MSW `payments.spec.ts`가 셀 링크로 상세를 연 뒤 환불까지 검증한다. 사람이 직접 클릭해 확인하지는 않았다.
- 실제 백엔드가 필요한 `tests/live/payments.spec.ts`는 셀 링크 기준으로 고쳤지만 실행하지 않았다.

- 상품 관리·입퇴실 이력·출퇴근·휴게 화면 적용은 #109에서 진행한다(위 재사용 방법 참고).
- `SalesPager`는 `SeatHistory`가 계속 쓴다. #109에서 입퇴실 이력을 옮길 때 함께 정리한다.
- 390px 결제 기간 입력 줄바꿈을 더 다듬을지는 #109에서 같은 형태를 적용할 때 함께 검토한다.
- `extended.spec.ts`(AI clarification)와 `profile.spec.ts`(닉네임 저장) MSW 시험 실패는 main에서도 재현된다. 이번 범위 밖이다.
