# 상품 유형·무기한·다지점·변경 이력 화면 (#7)

## 배경 / 문제

Frontend [#7](https://github.com/OpenStudyService/OpenStudy-Frontend/issues/7)은 상품 화면을 확정된 상품 계약으로 바꾸는 작업이다. 기존 화면은 일반 `ResourcePage`로 `price`·`amount`·`hourlyRate`·`days`를 단일 지점(`branchId: "all"`) 상품에 입력받았다. 이 모델에는 유형별 단위, 유효기간 없음(무기한), 여러 판매 지점, 분류, 변경 이력이 없다.

Backend [#16](https://github.com/OpenStudyService/OpenStudy-Backend/issues/16)([PR #38](https://github.com/OpenStudyService/OpenStudy-Backend/pull/38))이 main에 병합되어 실제 상품·분류 API가 생겼다. SRS v1.1의 상품 정책에 따라 물리 삭제는 제공하지 않고 판매 중지·재개로만 관리하며, 상품 유형은 등록 뒤 바꿀 수 없다.

Backend main `89f52e6`을 기준으로 정본 계약(OpenAPI `0.1.4-workspace`, `docs/design/foundation/product-api.md`)을 확인했다. Frontend main `90eab21`에서 `feature/product-screens`를 만들었다. 작업 전 프론트 작업 트리는 깨끗했다.

## 검토한 선택지

- **일반 ResourcePage에 필드를 추가한다 / 전용 화면을 만든다.** 유형별로 필드가 달라지고, 변경 이력·판매 지점·분류·판매 상태가 각각 다른 API와 권한을 쓴다. 범용 폼에 이 분기를 넣으면 다른 화면의 동작까지 복잡해진다. 지점·직원·초대 화면처럼 전용 `src/features/products`를 만들고 라우트만 교체했다.
- **수정 요청에 폼의 모든 값을 보낸다 / 바꾼 값만 보낸다.** 충돌(409) 뒤 최신 상품을 다시 읽으면, 전체 값을 보내는 방식은 건드리지 않은 필드로 다른 사람의 변경을 덮어쓴다. 폼이 시작된 시점의 상품(`base`)과 비교해 바꾼 필드만 최신 version으로 보낸다. `terms`는 서버 계약대로 바꿨다면 해당 유형 전체를 보낸다.
- **목 저장소의 기존 평면 상품 모델을 유지한다 / 정본 모델로 바꾼다.** 평면 모델을 유지하면 데모에서 상품 화면과 결제·이용권 흐름이 서로 다른 데이터를 보게 된다. 목의 `products`를 정본 형태(`terms`, `priceKrw`, `branchIds`, 이력)로 바꾸고, 목 결제의 이용권 발급은 `terms`에서 값을 계산하도록 고쳤다.
- **지점 변경 실패 시 선택 복귀.** 실패한 변경을 화면에 남기면 저장된 상태와 다른 선택이 보인다. 403·422 등 거부는 저장된 지점으로 되돌리고, 409만 입력을 유지해 최신 내용과 비교할 수 있게 했다.

## 결정 및 이유

- 계약의 `terms`를 그대로 따른다. 입력 단위를 라벨에 명시한다(시간권 분, 기간권 일, 정액권 원·시간당 원). 다른 유형의 필드는 화면에 나타나지 않고 요청에도 없다.
- 무기한은 `validDays: null`로 보낸다. 빈 입력이나 0을 무기한으로 해석하지 않고, 무기한 체크박스를 명시적으로 고르게 한다. 숫자 입력은 부호·소수·지수·앞자리 0을 거부한다.
- 판매 금액 0은 클라이언트에서 거부한다. Backend와 OpenAPI가 1 이상만 허용하기 때문이다. 이슈 본문의 검증 항목에 "0원"이 있어 이 해석을 아래 남은 작업에서 확인을 요청한다.
- 화면의 권한 표시는 힌트일 뿐이며 서버가 매 요청 다시 판정한다. 상품 수정은 서버가 준 `canEdit`을 따른다. 판매 상태·판매 지점·변경 이력은 모든 판매 지점에서 지점 관리자 + 운영 설정 권한이 있을 때만 보인다. 서버 403은 그대로 표시한다.
- 삭제 버튼과 삭제 호출을 만들지 않는다. 판매 중지·재개는 실행 전에 확인 단계를 둔다. 중지해도 기존 구매 내역과 이력이 보존된다고 안내한다.
- 분류는 모든 사용자에게 보이고, 등록·이름 변경·사용 중지는 사장님만 보인다. 코드와 유형은 등록 뒤 바꿀 수 없다는 서버 규칙을 안내한다. 분류 선택은 같은 유형의 활성 분류만 보여 주고, 이미 지정된 사용 중지 분류만 예외로 유지한다.

## 구현 내용

- `src/features/products/`: `Products.tsx`(목록·필터·탭), `ProductForm.tsx`(유형별 입력), `ProductCreate.tsx`(등록, 멱등 키), `ProductDetail.tsx`(수정·판매 상태·판매 지점·이력), `Categories.tsx`, `model.ts`(검증·요청 본문·권한 힌트·이력 차이), `hooks.ts`. 라우트 `/app/:scope/products`를 교체했다.
- 수정은 바꾼 필드만 전송한다. 변경이 없으면 요청하지 않고 안내한다. 409에서는 입력을 유지하고, 최신 정보 확인 시 서버 상품 내용을 해당 영역에만 보여 준다. 다음 저장은 최신 version과 사용자가 바꾼 필드만 보낸다.
- 변경 이력은 변경 전후 값을 변경된 항목만 보여 주고, 최초 이력은 전체 값을 보여 준다. 작업자는 직원 선택 데이터의 이름으로 표시한다.
- 목(MSW): `src/mocks/products.ts`가 상품·분류 10개 엔드포인트를 계약대로 구현한다(공유 상품 쓰기 권한, 지점 관리자 한정 판매 상태·지점·이력, 409 `latestVersion`·`reloadUrl`, 멱등 키 재전송, 삭제 405, 유형 변경 422). `src/mocks/terms.ts`는 목 결제의 이용권 발급 값을 계산한다. `schema.ts`의 `products`를 정본 형태로 바꾸고 `productCategories`를 추가했다. `catalog.ts`의 옛 상품 항목과 `domain.ts`의 상품 특례를 제거했다.
- 생성 타입: `foundation.generated.ts`를 Backend main의 OpenAPI로 다시 생성했다. 이미 최신이어서 변경은 없었다. 저장소의 `api:foundation` 스크립트는 형제 디렉터리 `openstudy-backend`를 읽어서, 별도 작업 트리에서는 병합된 OpenAPI를 임시 경로로 지정해 같은 도구를 실행했다.
- 변경하지 않은 것: 구매·결제·이용권 발급 화면. `GET /workspace/lookups`가 `products`를 비운 채 반환하는 점(Backend 문서에 명시)은 결제 화면의 상품 선택에 영향을 주지만 이 이슈의 범위 밖이다.

## 검증 결과

### 자동 검사와 MSW

- Node.js 24.19.0. `tsc -b`와 `eslint .` 통과(출력 없음). `npm run build`(live) 통과.
- Vitest 19개 파일, **161개 통과**, 실패·건너뜀 0(기존 125개 + 신규 36개).
    - `model.test.ts` 14개: 숫자 입력 경계, 유형별 `terms`, 무기한, 바꾼 필드만 전송, 권한 힌트, 이력 차이.
    - `Products.test.tsx` 13개: 단위·무기한 표시, 삭제 버튼 없음, 읽기 전용 안내, 유형별 전송 본문, 0원·빈 유효기간 차단, 유형 고정, 409 입력 유지와 덮어쓰기 방지, 판매 중지 확인, 지점 변경 실패 시 복귀, 이력 표시, 분류 권한.
    - `mocks/products.test.ts` 9개: 목 계약(가시성·`canEdit`, 멱등, 입력 검증, 공유 상품 쓰기 거부, 409, 유형 변경 금지, 판매 지점 관리자 한정, 삭제 405, 분류 권한).
- Chrome Playwright 목 모드: 기존 `smoke`·`responsive`(390px 포함)·`workflows`(상품 구매 흐름 포함) 통과, 신규 `products.spec.ts` 2개 통과(사장님 등록·수정·중지·이력, 직원 읽기 제한).
- 첫 전체 실행에서 신규 시험 1개가 실패했다. 최신 서버 내용 안내 문구가 세 영역에 동시에 나타나는 화면 결함이었다. 충돌이 난 영역에만 보이도록 고쳤다. 나머지 실패는 시험 쿼리 오류였고 시험 기대값을 바꿔 덮지 않았다.

### 실제 서버(별도 DB) 연동

Backend main `89f52e6`을 별도 작업 트리에서 `bootJar`로 빌드했다. 사용자의 개발 DB와 포트를 쓰지 않고, 임시 Docker MySQL 8.4(포트 3317)에 Flyway V1~V3을 적용한 뒤 `ownerBootstrap`으로 사장님을 만들고 지점 2개·분류 3개를 사장님 API로 등록했다. 지점 관리자와 일반 직원 계정은 비밀번호 해시를 SQL로 넣었다(초대 메일 흐름은 이 검증 범위가 아니다). 검증 뒤 서버·컨테이너·임시 작업 트리를 삭제했다. 시험 코드는 저장소에 넣지 않았다.

Vite live 모드(포트 5199, 프록시)와 Chrome으로 확인했다.

- 사장님: 빈 목록, 시간권 무기한 상품을 두 지점에 등록(`validDays: null`), 가격 수정(요청 본문이 `{version, priceKrw}`뿐), 판매 중지·재개, 판매 지점 축소, 변경 이력에 `15,000원 → 16,000원`·`판매 중 → 판매 중지`·`강남점, 성수점 → 강남점`·최초 등록 표시. 삭제 버튼 없음, 직접 `DELETE`는 405, 가격 0은 화면에서 차단되고 직접 호출은 422.
- 동시 수정: 다른 클라이언트가 이름을 바꾼 상태에서 가격만 수정하면 실제 409, 입력 유지, 최신 서버 내용 표시, 재저장 요청이 `{최신 version, priceKrw}`뿐이며 최종 상품에 다른 사람의 이름과 내 가격이 함께 반영됨.
- 지점 관리자(강남): 두 지점이 공유한 상품은 읽기 전용 안내, 판매 상태·이력 영역 없음, 직접 수정은 403. 강남 전용 상품은 등록·판매 중지·이력 확인 가능, 보이지 않는 지점 추가는 403.
- 일반 직원(운영 설정 권한만): 등록·수정은 가능, 판매 상태·이력 영역이 없고 직접 호출은 403. 분류는 읽기 전용.
- 분류: 사장님이 등록·사용 중지하면 등록 화면에서 해당 분류가 사라짐.
- 실행 중 5개 시나리오가 모두 통과했다. 일부는 시험 스크립트의 가정(재실행 시 같은 값으로 저장하면 변경 없음 처리, 선택자 모호함) 때문에 고쳐 다시 실행했다. 제품 코드의 결함은 아니었다.

### 하지 못한 검증

- 판매 중지 후 새 판매 차단과 재개 후 정상 판매: 구매 API가 아직 없어 확인하지 못했다. Backend는 `requireSellable`을 서비스 계약으로만 제공했다.
- 기존 구매 표시 보존: 구매 흐름이 없어 실서버로 확인하지 못했다. 변경 이력의 이전 값 보존만 확인했다.
- SSE 이벤트로 다른 브라우저 화면이 갱신되는 흐름: 확인하지 않았다. Backend 문서상 `products` 이벤트는 기록만 확인됐다.
- 운영 환경(HTTPS 프록시, 실제 배포): 하지 않았다. Infra 범위다.

## 남은 작업 / 보류 사항

- **0원 상품 정책 확인.** 이슈 검증 항목에 "0원"이 있으나 Backend는 DB 제약 `price_krw>0`과 OpenAPI 최솟값 1에 따라 0원을 거부한다. 0원 허용이 의도라면 Backend 정책과 DB 변경이 먼저 필요하다.
- 결제 화면의 상품 선택은 `GET /workspace/lookups`의 `products`가 비어 있는 동안 실서버에서 선택지가 없다. 구매 이슈에서 상품 목록 API를 쓰도록 바꿔야 한다.
- 변경 이력은 과거에 판매한 모든 지점의 관리 권한을 요구한다(Backend 계약). 판매 지점이 늘어난 상품은 일반 지점 관리자가 이력을 볼 수 없다.
- 분류 이름 변경 중 409가 나면 수정 폼의 version이 낡은 채 남는다. 목록은 갱신되므로 폼을 다시 열면 해결된다. 사용 빈도가 낮아 이번에는 처리하지 않았다.
- 목록은 이름순 20개씩 페이지를 쓴다. 정렬 변경 UI는 만들지 않았다.
- 이슈 #7의 체크박스는 변경하지 않았다. PR 병합 뒤 검증 결과를 보고 정리한다.
