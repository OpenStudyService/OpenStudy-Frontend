# 2026-11-02 채팅·채널·업무 카드 정본 API 연결 (#27)

## 1. 배경 / 문제

Frontend #27의 기존 화면 준비 PR #48과 업무 연결 PR #54는 병합됐지만 채팅은 구 데모 API를 사용했다. 이슈·코드·개발 기록과 Backend #74·#76·#77, 현재 main 계약을 확인하고 Frontend main `2897b05`에서 `feature/chat-api-integration`을 만들었다. 기존 미추적 `.gitattributes`와 Backend 작업 트리의 `poc.env`는 변경하거나 포함하지 않는다.

사용자가 서브에이전트 작업을 명시해 계약 감사, API 어댑터, UI·세션·정렬을 분담했다. 주 에이전트가 통합 검토·실제 서버 시험·과거 카드 갱신·읽음 보류·문서·PR을 맡았다.

## 2. 검토한 선택지

- 화면을 모두 정본 DTO로 교체하거나, 기존 화면 모델을 유지하면서 live 정본 어댑터를 두는 방법을 검토했다. 이미 검증한 입력·재전송·스크롤·데모 DM 동작을 재사용하도록 후자를 선택했다.
- 채널 단일 읽음과 본문·스레드별 독립 읽음의 차이를 사용자에게 예시로 설명했다. 본문을 읽으면 열지 않은 이전 답글도 읽음이 되는 현 서버 방식으로 바꾸는 선택지는 사용자가 채택하지 않았다.

## 3. 결정 및 이유

- 사용자는 **독립 읽음 정책 유지와 필요한 Backend 선행 작업 분리**를 선택했다. [Backend #155](https://github.com/OpenStudyService/OpenStudy-Backend/issues/155)를 등록했다. live에서는 잘못된 읽음 요청을 보내지 않고 읽지 않음 배지도 보류한다. 준비 안내를 표시하며 #27 전체를 완료 처리하지 않는다. MSW 독립 읽음은 기존 동작을 유지한다.
- 정본 메시지 ID는 bigint 문자열이다. numeric sequence를 만들어 정밀도를 잃지 않도록 ID를 그대로 보존하고 BigInt로 정렬·페이지 경계 비교를 한다.
- 채널 정보 PATCH와 참여자 PUT은 별도 명령이다. PATCH 응답의 version을 다음 PUT에 사용하고 최종 상세를 다시 읽는다. 일부 저장 후 실패는 명확히 안내하고 최신값 비교를 요구한다. 클라이언트에서 원자적 저장처럼 가장하지 않는다.
- 후보는 id/name 최소 응답을 그대로 사용한다. 채널 실제 참여자는 별도 members 응답으로 확인하고 이름·서버 canManage를 표시한다. 생성은 단일 POST에 참여자를 포함하고 같은 입력의 재시도 키를 유지한다.
- 업무 카드는 조회 시점 서버 snapshot으로 표시하며 접근 불가 카드의 null 제목·ID를 과거 데이터로 보충하지 않는다. 과거 페이지 카드도 새로고침에서 메시지 단건 API로 갱신해 원본 변경·권한 회수를 반영한다.

## 4. 구현 내용

- live 채널·관리 채널·후보·참여자·원문·스레드·단건·전송·업무 공유·생성·수정·참여자 변경을 정본 경로/DTO에 연결했다. 런타임 검증으로 대화 범위 불일치·잘못된 응답·과도한 정보가 담긴 접근 불가 카드를 거절한다.
- 실제 작성자 이름·참여자 수·업무 카드 snapshot을 표시한다. 일반 Mock 통신·기존 DM·데모 읽음 흐름은 보존한다.
- 404 참여 종료에서 초안·전송 대기·개인 캐시를 정리한다. 화면 이탈 후 도착한 과거 페이지가 대화를 복원하지 않도록 요청 취소를 확인한다.
- 실제 서버 시험 명령과 재현 문서, bigint·과거 카드·부분 저장·읽음 보류 회귀 검사를 추가했다.

## 5. 검증 결과

- 서브에이전트 집중 검사: API 10개, UI·세션·모델 21개, 최종 채널 관리 4개 통과. 통합 과정에서 린트의 불필요한 total 초기값과 기존 테스트의 구 채널 응답/데모 모드 가정을 보완했다.
- 실제 Backend main `18d6826`를 별도 추출·빌드하고 일회용 MySQL·Chrome으로 4개 시나리오를 통과했다(43.0초). 채널 생성 응답 유실·같은 키 재시도, 과거 업무 카드 현재 상태·타 지점 접근 불가, 편집 409·다른 필드 보존·참여자 저장, 50건 초과 과거 조회·스레드·스크립트 텍스트·전송 응답 유실·참여 종료를 확인했다.
- 첫 실제 시험은 textarea와 전송 메시지를 동시에 찾은 선택자 문제로 실패했다. article로 범위를 좁히고 입력 초기화도 기다린 뒤 통과했다.
- 독립 읽음 미지원 상태에서 live가 채널 단일 읽음 API를 호출하지 않음을 확인했다. 독립 읽음의 실제 저장 검증은 수행하지 않았다.
- live/mock 빌드·산출물 오염 검사와 Chrome 산출물 검사 5개 통과. 기존 500KB chunk 경고는 남는다.
- 실제 업무 상세 모바일 캡처를 확인했다. 실제 서버에는 로컬 프로필의 일부 공통 선택 데이터 샘플이 있어 별도 업무 데이터의 API 저장·조회와 구분한다.
- 중간 승인 검토 사용량 제한으로 실제 검증 재시도 한 번이 실행되지 않았다. 사용자의 재개 요청 후 같은 승인 경로로 실행하여 통과했다. 제한을 우회하지 않았다.

## 6. 남은 작업 / 보류 사항

- Backend #155의 계약·저장·API 준비 후 본문·스레드 독립 읽음·미확인 수를 연결하고 두 브라우저로 검증해야 한다. #27은 열린 상태를 유지한다.
- 실제 참여자를 얻기 위한 채널별 members 요청, 로드된 카드별 단건 재조회가 추가된다. 대량 채널·메시지의 처리량과 요청 수 최적화는 후속 검토 대상이다.
- 운영 배포·부하·다중 인스턴스·실제 모바일 기기, 신규 DM·채팅 실시간 수신은 이번 범위가 아니다. Backend 자체 통합 테스트는 재실행하지 않았다.
- main 직접 push·병합·자동 병합은 수행하지 않는다. 구현·검증한 작업 브랜치와 PR만 준비한다.

## 통합 검증 및 보완

- `npm run check` 최종 통과: typecheck·lint, Vitest 50개 파일 422개, 메일 도구 9개, 빌드 가드 19개. 메일 도구 시험은 실제 발송 검증이 아니다.
- 과거 페이지의 카드도 서버 단건 메시지로 재검증하는 회귀 검사를 추가했다. 현재 선택 지점과 다른 허용 지점의 카드 상세는 업무 지점으로 이동해 열도록 보완했다. 다른 지점 상세 이동의 실제 서버 브라우저 시나리오는 별도로 수행하지 않았다.
- 실제 검증 후 PID 명령줄의 jar 경로와 컨테이너 ID·이름을 대조해 이번 서버·DB만 종료·제거했고 임시 자격 증명 파일을 삭제했다.
- graphify 갱신 1,904 nodes / 5,672 edges 확인. 그래프는 저장소 방침대로 로컬 출력이다.
- 전용 Mock 포트의 Chrome 회귀 24개 전체 통과(5.1분): 독립 읽음 데모·참여 회수·전송 재시도·과거 메시지·카드 권한·공유·기존 DM·한글 조합·업무·세 테마·1440/1024/390px·전체 화면. 초기 Worker 준비/일부 테스트의 세션 전환 과정에서 Vite의 실제 API 프록시 ECONNREFUSED 로그가 있었지만 해당 회귀 단언은 모두 통과했다.
- 마지막 카드 상세 지점 이동 보완 후 타입 검사와 카드 집중 검사 3개 및 live/mock 빌드·오염 검사를 재확인했다. 최종 그래프는 1,905 nodes / 5,673 edges다. `git diff --check` 통과.
