# 버튼 역할별 색상 정리 계획

작성일: 2026-11-18. 상태: 조사·계획 완료, 구현 전.

후속: 이 계획에 대한 사용자 승인 후 [구현·검증 기록](../development-log/2026-11-18-button-action-colors.md)을 추가했다. 아래 내용은 계획 당시의 기준과 조사 결과를 보존한다.

## 목적과 조사 범위

버튼의 색상으로 주요 실행, 보조 조작, 데이터 삭제·취소·접근 제한을 구분한다. 지점 저장 버튼 수정인 [PR #150](https://github.com/OpenStudyService/OpenStudy-Frontend/pull/150)을 기준 사례로 삼는다.

프런트엔드 `src/`의 테스트를 제외한 TSX를 AST로 조사해 `Button`·네이티브 `button` 선언 314개를 확인했다. 공통 컴포넌트, 직접 지정한 클래스, 조건부 variant, 공통 액션 렌더러와 실제 서버 호출을 함께 검토했다. 선언 하나가 여러 행이나 화면에서 재사용되므로 선언 수와 사용자에게 보이는 버튼 수는 다르다.

검토 기준 코드는 PR #150 작업 브랜치의 cc890de이다. 계획 문서는 main 기준 `docs/button-style-plan` 브랜치에 작성한다. 이후 구현은 PR #150 반영 여부와 최신 main을 다시 확인하고 시작한다. 현재 조사는 정적 코드 검토이며 모든 상태의 브라우저 재현을 완료한 것은 아니다.

## 1. 색상 적용 기준

| 역할 | 적용할 스타일 | 예시와 판단 기준 |
| --- | --- | --- |
| 주요 실행 | `primary`: 현재 테마의 주요 색상 | 등록·저장·신청·승인·정상 처리. 폼이나 독립 작업 영역에서 대표 실행을 강조한다. |
| 보조 조작 | 기본 버튼: 중립적인 테두리·배경 | 편집 화면 열기, 조회, 재시도, 상세 보기, 창 닫기, 입력 취소. |
| 낮은 강조 | `quiet`: 투명 배경과 보조 글자색 | 검색 조건 초기화, 뒤로 가기 등 우선순위가 낮은 조작. |
| 위험 작업 | `danger`: 공통 위험 색상 | 데이터 삭제, 환불·서버 취소, 반려, 운영 중단, 접근 제한, 계정 초기화. |

### 세부 원칙

- ‘취소’라는 문구를 보고 자동으로 위험 색상을 지정하지 않는다. 입력창만 닫는 취소와 실제 예약·신청을 취소하는 동작을 구분한다.
- 같은 버튼이 중단과 재개, 취소와 정상 처리에 공용이면 현재 실행할 동작으로 variant를 결정한다.
- 기존 대상이 제한 상태라는 이유만으로 저장 버튼을 위험 색상으로 만들지 않는다. 이번 제출에서 제한·중단·회수로 전환하는지를 확인한다.
- 운영 중단·이용 제한에서 정상 상태로 복구하는 실행은 `primary`로 표시한다.
- 퇴근·휴게 종료·예약 이용 완료·퇴실·사물함 반납은 정상 업무 흐름으로 분류해 `primary`를 유지한다. 환불·예약 취소와 구분한다. 별도의 업무 정책을 바꾸지 않는다.
- 주요 버튼 개수는 페이지 전체가 아니라 폼·편집 영역을 기준으로 판단한다. 목록의 보조 작업까지 모두 채워진 색상으로 바꾸지 않는다.
- 위험 색상은 삭제·반려·환불 등의 문구와 함께 사용한다. 아이콘 버튼에는 접근성 이름을 유지한다.
- 로딩·비활성 상태에서도 작업의 의미를 유지한다. 색상 변경 때문에 비활성 버튼이 활성화되거나 이벤트가 달라져서는 안 된다.

## 4. 보조 버튼과 공통 렌더러

- 조회·기간 적용·상세 보기·검색·재시도·내보내기·뒤로 가기·패널 닫기·입력 취소는 중립 스타일을 유지한다. `type="submit"`이라는 이유만으로 primary를 강제하지 않는다.
- 결제 목록의 **초기화**, 매출 화면의 **조건 초기화**는 다른 목록과 같은 quiet로 정리한다. 실제 데이터를 지우는 가상 데이터 초기화와 구분한다.
- `ResourcePage`의 공통 액션 진입은 `danger` 정보를 받지만 `ResourceForm`의 확정 버튼은 primary로 고정되어 있다. 현재 실제 메뉴에서 이 경로를 사용하는지를 확인하고, 도달 가능한 위험 명령에만 submit variant를 전달한다. 메타데이터만 남은 예전 화면을 실제 문제 수로 중복 집계하지 않는다.
- `catalog.ts`에서 정상 업무의 퇴실·반납까지 danger로 지정한 기존 정의가 있다. 실제 전문 화면과 적용 경로를 대조해 도달 가능한 정의를 위 기준으로 맞춘다. 사용하지 않는 경로를 새로 활성화하지 않는다.
- 공통 `Button`은 variant가 임의 문자열이다. 현재 사용 중인 기본값·primary·quiet·danger를 타입으로 제한하고, `Panel.closeButtonVariant` 등 전달 속성에도 같은 타입을 사용한다. 버튼의 기본값은 중립 스타일로 유지한다.
- 공통 danger는 현재 빨간 글자만 지정되어 일반 버튼의 테마별 호버 배경·포커스 효과를 상속한다. 위험 전용 글자·테두리·옅은 배경·호버·포커스 색을 공통 토큰으로 정리한다. 버튼 크기·배치와 정상 primary 팔레트는 기존 체계를 사용한다.

## 5. 구현 순서와 PR 단위

하나의 색상 기준이 여러 업무 화면에 적용되는 변경이므로 **하나의 리뷰 가능한 PR**을 목표로 한다. 구현 중에는 다음 순서로 나누어 확인한다.

1. **공통 기준 확정**: Button variant 타입과 danger 상태별 스타일을 정리한다. 기본 버튼을 primary로 바꾸는 전역 기본값 변경은 하지 않는다.
2. **위험 작업부터 반영**: 실제 취소·삭제·반려·환불·병합·운영 중단·접근 제한과 반대 동작을 분리한다. 공통 요청 카드와 조건부 상태 저장을 먼저 처리한다.
3. **주요 실행·보조 스타일 통일**: 14개 누락 위치, 승인, 체크 항목 저장, 목록 초기화를 적용한다. 이미 올바른 주요 실행 버튼은 회귀 점검한다.
4. **브라우저 검증·개발 기록·PR 작성**: 상태별 매핑과 접근성을 확인하고, 실제 검증 결과·미검증 항목을 구분해 기록한다. 작업 브랜치 push와 PR 생성 후 사용자 병합 대기로 둔다.

착수 브랜치 예: `fix/button-action-colors`. 최신 main에서 생성한다. PR #150과 같은 파일을 수정하므로 반영 여부를 확인하고 중복 변경을 제외한다.

## 6. 검증 계획과 인수 조건

### 자동 검증

- 구현 중: 변경 파일에 대한 `npx vitest related <수정 파일> --run`.
- 조건부 색상은 의미 있는 상태 조합으로 검증한다: 승인/반려/취소, 예약 시작/완료/취소·환불, 판매 중지/재개, 운영 중단/재개, 계정 제한/복구, 소속 회수/일반 저장.
- 미변경 상태로 이름 등만 저장할 때 불필요하게 danger가 되지 않는지 검증한다.
- 공통 폼의 위험 명령 전달과 네이티브 삭제 버튼의 접근성 이름을 확인한다. 모든 단순 버튼의 클래스명을 반복 확인하는 테스트를 양산하지 않는다.
- 커밋 전: `npm run typecheck`, `npm run lint`, 관련 테스트.
- PR 전: `npm test`, `npm run build`, `graphify update .`.

### 브라우저 검증

- Chrome MSW에서 OWNER·관리자·직원의 권한별 노출과 disabled·로딩·충돌 상태를 확인한다.
- 포레스트·네이비·샌드 테마의 기본·호버·키보드 포커스·비활성 색상과 대비를 확인한다.
- 1440·1024·390px에서 주요/위험 버튼, 동적 상태 전환, 확인·입력 취소를 확인한다. 버튼 순서·문구·폭과 포커스 표시도 확인한다.
- 환불·계정 초기화·병합 등 검증용 변경은 격리된 mock 데이터로 수행한다. 실제 Backend 검증 여부는 별도로 표시한다.

### 완료 조건

- [ ] 14개 주요 실행 누락 위치가 분류표에 맞게 표시된다.
- [ ] 위험 작업 표의 각 행에 적용 결과 또는 현재 경로가 사용되지 않는다는 근거가 남아 있다.
- [ ] 같은 공용 버튼의 위험 실행과 정상 실행이 올바르게 구분된다.
- [ ] 폼을 닫는 취소·검색 초기화가 위험 작업으로 오인되지 않는다.
- [ ] 정상 업무 완료·퇴실·반납은 승인된 주요 작업 스타일을 유지한다.
- [ ] 색상 외에도 작업 문구·접근성 이름으로 의미를 알 수 있다.
- [ ] 기존 권한·비활성·로딩·충돌·멱등성·확인 절차와 서버 요청 내용이 유지된다.
- [ ] 필수 자동 검증과 브라우저 검증 결과가 개발 기록·PR에 구분되어 있다.
