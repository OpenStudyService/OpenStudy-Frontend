# 실제 수신함으로 직원 초대 검증

관련 이슈: [Frontend #6](https://github.com/OpenStudyService/OpenStudy-Frontend/issues/6), [Backend #14](https://github.com/OpenStudyService/OpenStudy-Backend/issues/14), [Backend #18](https://github.com/OpenStudyService/OpenStudy-Backend/issues/18).

`npm run test:e2e:real-mail`은 실제 프론트와 서버를 대상으로 운영자가 진행하는 신규 계정 초대 흐름을 관찰한다. SMTP나 수신함 자격증명은 프론트 도구에 전달하지 않는다. 관리자는 직접 로그인·초대·승인하고, 수신자는 실제 받은 링크를 별도의 직원 브라우저 창에서 연다. 도구가 메일을 읽거나 자동 발송하지 않는다.

기존 [`npm run test:e2e:live`](./invitation-live.md)는 일회용 MySQL과 Mailpit을 사용하는 별도 자동 회귀다. Mailpit 성공, 실메일 도구 자체의 시험 성공, 실제 외부 수신함 성공을 각각 구분해 기록한다.

## 준비할 환경

- MSW를 사용하지 않는 프론트 URL과 그 프론트의 `/api`에 연결된 실제 Backend. 로컬에서는 기존 `dev:live`의 `API_PROXY_TARGET`으로 연결할 수 있다. 배포된 프론트도 같은 `/api` 경로를 사용해야 한다.
- Backend #14의 SMTP 설정, 실제 발신 주소, 발신 도메인·TLS 설정. 초대 수락 주소는 테스트할 프론트의 `/invitations/accept`여야 한다. 비밀값은 Backend 실행 환경에서 관리한다.
- 초대 관리 권한이 있는 관리자 계정과 운영 중인 테스트 지점.
- 테스트 담당자가 사용할 수 있는 **아직 가입하지 않은 실제 수신 이메일 하나**. 도구는 이 주소로 향하는 초대 생성 요청 한 건만 허용한다.
- Node.js 24와 Chrome. 프론트·API 서버는 도구 실행 전에 별도로 기동한다.

로컬 서버를 사용하는 경우 메일 링크는 그 로컬 프론트를 실행한 컴퓨터에서 연다. 다른 기기에서 `127.0.0.1` 링크를 열면 원래 서버에 연결되지 않는다. 배포 환경에서는 Backend #29의 HTTPS·프록시 연결 조건을 먼저 확인한다.

## 실행

사용법은 서버나 브라우저를 시작하지 않고 확인할 수 있다.

```powershell
npm run test:e2e:real-mail -- --help
```

아래 주소와 이메일을 실제 검증 환경으로 바꾼다. 비밀번호나 수신 링크를 명령행·환경변수에 넣지 않는다.

```powershell
$env:INVITATION_REAL_MAIL_BASE_URL='http://127.0.0.1:15176'
$env:INVITATION_REAL_MAIL_RECIPIENT='담당자가-사용할-실제-수신-이메일'
$env:INVITATION_REAL_MAIL_TIMEOUT_MINUTES='15'
npm run test:e2e:real-mail
```

`BASE_URL`은 경로·쿼리·fragment·자격증명이 없는 origin이다. HTTPS 또는 loopback HTTP만 허용한다. 전체 대기 시간은 기본 15분이며 1~60분으로 설정할 수 있다. 관리자와 직원의 세션은 서로 다른 임시 브라우저 context로 분리된다.

## 신규 계정 진행 순서

1. 관리자 창에서 로그인하고 테스트 지점의 **직원 관리 → 초대·승인**으로 이동한다.
2. 지정한 수신 이메일, 테스트 직원 이름, 일반 직원 역할과 필요한 최소 권한을 입력하고 발송을 한 번 요청한다. 선택 지점·수신 주소를 제출 전에 확인한다.
3. 관리자 상세에서 초대 상태와 발송 상태를 각각 확인한다. SMTP 발송 완료 표시와 실제 수신함 도착은 서로 다른 결과다. 필요하면 **초대 상태 새로고침**을 사용한다.
4. 실제 수신함에서 발신자·제목·도착 시각·스팸함 여부를 확인한다. **직원 창의 주소 표시줄**에 실제 받은 링크를 열고 새 계정 비밀번호를 설정해 수락한다. 도구가 연 직원 창을 사용해야 관찰할 수 있다. 토큰이 있는 전체 주소를 채팅이나 기록에 붙이지 않는다.
5. 직원 창에서 로그인하고 승인 대기 화면을 확인한다. 관리자 창의 열린 상세가 승인 대기로 갱신되는지 확인한 뒤 최종 승인한다.
6. 직원 창의 승인 상태가 갱신돼도 업무 진입에는 재로그인이 필요한지 확인한다. **다시 로그인**을 누르고 로그인하여 초대한 지점 업무 화면에 진입한다.
7. 터미널의 관찰 결과와 실제 수신함 확인 결과를 아래 형식으로 남긴다. 실패하거나 시간이 초과되면 생성된 초대 상태를 관리자 화면에서 확인한다. 테스트를 다시 실행한다고 기존 초대가 정리되지는 않는다.

도구의 성공은 관찰한 API·화면 순서의 성공이다. 메일의 출처·실제 수신·스팸 분류는 운영자의 확인 결과를 함께 남겨야 한다. 기존 계정, 재발급, 반려는 이 신규 계정 smoke의 자동 관찰 범위가 아니다.

## 추가 수동 검증

아래는 같은 smoke를 무작정 반복하지 않고 별도의 테스트 주소·지점을 정해 수행한다.

| 시나리오 | 확인할 결과 |
| --- | --- |
| 기존 직원의 추가 지점 | 기존 계정으로 수락하고 기존 비밀번호·업무 세션·소속을 유지한다. 추가 승인 후 새 지점에 접근한다. |
| 다른 계정으로 로그인한 상태의 신규 링크 | 명시적으로 로그아웃한 뒤 같은 화면에서 신규 수락을 계속할 수 있다. |
| 재발급 | 새 메일이 도착하고 이전 메일의 링크는 거부된다. |
| 취소·만료 | 해당 링크에서 수락할 수 없다. 실제 환경의 DB 기한을 직접 바꾸지 않는다. 만료는 정상 기한 경과 또는 전용 테스트 환경에서 확인한다. |
| 반려 | 관리자 입력 사유가 직원 승인 상태 화면에 표시된다. |
| 권한·연결 변경 | 관리자 권한 회수 후 명령이 차단된다. 연결 단절 시 새로고침·오류 안내를 확인한다. |

## 기록과 완료 범위

실행 결과에는 날짜, Frontend/Backend 커밋, 환경 URL, SMTP 제공자·발신 도메인, 테스트 지점, 시나리오별 통과·실패·미검증, 수신·스팸 분류 확인, 남은 작업을 적는다. 수신자 개인정보는 필요한 범위만 남기고, 전체 메일·비밀번호·토큰·수락 링크·쿠키는 기록하지 않는다.

도구는 trace, screenshot, video, 영구 로그인 상태, 수신함 연동을 만들지 않는다. 실패 시에도 브라우저의 원시 오류·요청 본문·링크를 결과에 복사하지 않는다. 실행 도중 운영자가 별도로 켠 화면 녹화·개발자 도구 기록은 도구가 관리하지 않는다.

실제 운영 SMTP·HTTPS 쿠키·CSRF·SSE·프로세스 재시작 검증과 Backend #18 전체 인수는 별도 조건이다. 도구를 준비하거나 테스트가 통과한 사실만으로 Frontend #6·Backend #14·#18을 종료하지 않는다.

도구 회귀만 실행할 때는 아래 명령을 사용한다. 이 시험은 외부 메일을 보내지 않으며 실제 SMTP 성공으로 집계하지 않는다.

```powershell
npm run test:real-mail:tool
```
