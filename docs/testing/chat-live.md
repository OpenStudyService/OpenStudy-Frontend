# 채팅 실제 Backend·DB 검증

Frontend #27의 정본 API 연결을 MSW와 구분해 검증한다. 독립 읽음은 Backend #155 선행 작업이며 이번 시험은 읽음 완료를 검증하지 않는다.

## 환경 준비

- Node 24, Chrome, Java 21, MySQL 8.4를 사용한다.
- Backend main `18d682645b90c707d5b54f380bb2494249a70641`를 별도 디렉터리에 추출하고 `bootJar`로 빌드한다. 기존 Backend 작업 트리·환경 파일·개발 DB를 사용하지 않는다.
- 일회용 DB `chat_live`를 loopback 13324에서 제공한다. Backend의 DB 환경 변수는 해당 DB만 가리키며 포트는 18094다. 메일 발송은 비활성화한다.
- Flyway 적용 후 공식 `ownerBootstrap`으로 `owner@chat.test`를 생성한다.
- 지점 1·2와 7요일 운영시간을 만든다. 지점 1 STAFF `staff@chat.test`의 ID는 2, 지점 2 STAFF `cashier@chat.test`의 ID는 3이다. 세 계정은 검증 전용 무작위 비밀번호를 공유한다.
- 테스트는 실제 API로 채널·메시지·업무를 생성한다. 직원 fixture는 일회용 DB에만 적용한다.

## 실행

프로세스 환경 변수 `CHAT_LIVE_PASSWORD`에 검증 비밀번호를 지정하고 실행한다.

```powershell
npm run test:e2e:chat:live
```

Vite live 15185에서 Backend 18094로 프록시한다. Service Worker를 차단하며 trace는 저장하지 않는다. 결과와 캡처는 git에서 제외된 `qa-artifacts/chat-live/`에 저장한다.

## 확인 범위

1. 채널 생성 응답이 실제 커밋 뒤 유실된 경우, 입력·동일 본문·동일 멱등 키로 재시도하고 채널이 하나만 남는지 확인한다. 빈 참여자 선택은 생성자 자동 참여를 사용한다.
2. 최신 페이지 밖의 업무 카드를 불러온 뒤 원본 상태를 변경하고 재조회하여 현재 상태를 표시하는지 확인한다. 타 지점 참여자는 업무 제목·식별자를 볼 수 없고 접근 불가만 표시한다.
3. 채널 편집의 실제 409에서 입력을 보존하고 최신값 확인 후 변경한 필드만 저장한다. 이름 수정이 다른 세션의 설명 변경을 덮어쓰지 않는지, 정보·참여자 변경 뒤 버전과 저장 결과가 맞는지 확인한다.
4. 50건을 넘는 메시지의 과거 조회, 스크립트 문자열의 텍스트 표시, 실제 답글 저장, 전송 응답 유실 후 같은 clientMessageKey 재전송과 중복 방지, 참여자 제거 뒤 목록·직접 주소·API 접근 차단을 확인한다.
5. live 화면에서 채널 단일 읽음 API가 호출되지 않는지 확인한다. 독립 읽음 완료를 대신하는 검증은 아니다.

## 정리와 한계

PID의 명령줄·jar 경로와 컨테이너 ID·이름을 대조해 이번 시험 서버·DB만 종료·제거하고 임시 자격 증명 파일을 삭제한다. 운영 배포·부하·실제 모바일 기기·다중 인스턴스·신규 DM·채팅 실시간 수신은 검증 범위가 아니다. Backend 자체 통합 테스트는 재실행하지 않는다.
